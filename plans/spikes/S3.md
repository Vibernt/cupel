# S3: Do the tests detect faults in critical code?

## Question

Do Vibernt Assay's tests detect faults in its permissions, agent-connect and billing code? We need four things:

- the mutation score per module
- the mutants that survive
- the tests with unique kills
- the mutation rate (mutants per minute)

The spike also decides D6, the JavaScript parser for mutation.

## Method

The code is in `plans/spikes/s3/`. It uses Node's standard library only and has no dependencies. Usage is in the comment at the top of each file.

1. **Lexer** (`lexer.mjs`). A small tokenizer that skips strings, template-literal text, comments and regex literals. It keeps a stack of open braces (for `${ }`) and a stack of open parentheses (so it knows the `)` that closes an `if (...)`). It decides "regex or division" from the previous token. One case is known to be wrong: a regex right after the `}` of a block.
2. **Operators** (`mutate.mjs`). They work on tokens:
   - comparison flip (`===`↔`!==`, `<`→`>=`, and so on)
   - boundary (`<`↔`<=`, `>`↔`>=`)
   - `true`↔`false`
   - `&&`↔`||`
   - negating an `if` or `while` condition (`if (!(…))`)
   - removing a `!`
   - arithmetic swaps (`+`↔`-`, `*`↔`/`, `%`→`*`, `+=`↔`-=`, `++`↔`--`). A `+` next to a string or template literal is skipped
   - return-value replacement (`return e` → `return undefined`, and `true`↔`false`)
   - removing a statement that is only a call (`[await] f(...);` → `;`)

   Mutants that produce identical text are merged. A cheap filter marks mutants inside `console.*(…)` calls, or that remove one, as meaningless. Ids are stable (`file:line:col:operator:replacement`). The sample is a seeded Fisher-Yates shuffle, so the same seed and inputs give the same mutants in the same order (checked: two runs gave the same SHA-256).
3. **Validity filter**. Each mutant is compiled with `new vm.SourceTextModule(text)`, which parses ES modules. It needs `node --experimental-vm-modules`. `new vm.Script` cannot parse `import` or `export`. The filter takes 0 to 99 ms per file.
4. **Mutants are served, not written** (`hook.mjs`). A `module.registerHooks` load hook, set through `NODE_OPTIONS=--import`, serves the mutant in place of the module's URL. It also reaches child processes. The snapshot's files are never written in the main run, so mutants can run in parallel. The hook records that the mutant was loaded: it was loaded for every mutant that ran.
5. **Test selection by block coverage**. Each of the 421 test files ran alone with `NODE_V8_COVERAGE`. For each mutant, we selected the test files where V8's innermost block range that contains the mutant's offset has a count above zero. The static import closure was computed only for comparison. Files are run most hits first, then fastest first.
6. **Runs**. Each selected file runs in its own process: `node --test --test-isolation=none --test-reporter=reporter.mjs`. A small JSON reporter writes one line per test with its pass or fail.
   - A mutant counts as killed only when the reporter shows a failing test. A module that fails to load is reported as a failing test named after the file.
   - A timeout counts as a kill but is reported separately. The limit is 3× the file's baseline time, with a floor of 2 s.
   - A non-zero exit with no failing test is an environment error. It is neither a kill nor a survival, and the mutant is re-run.
   - Timeouts were re-run with 2 processes and a 10× limit (`recheck`).
   - agent-connect and billing ran the full matrix: every selected file for every mutant. permissions stopped a mutant once 2 files had killed it. This keeps uniqueness exact (a unique kill needs exactly one killing file), but the count of killing tests for widely killed mutants is incomplete.
7. **Caps**. At most 150 mutants per module, and at most 30 minutes per module. Only billing (741 mutants) was sampled.
8. **Comparison with a real parser** (`compare-ast.mjs`). It used acorn 8.19.0, read-only from `/opt/homebrew/lib/node_modules/eslint/node_modules/acorn` (nothing was installed). It compared tokens and mutation sites with the lexer over all of Assay's `src/` and `public/`.
9. **File mode** (`file-mode.mjs`). A small number of mutants were written to disk to see what source-text tests do. Each file was restored right after, and its SHA-256 was checked.

### Source-text pins (file mode)

The hook serves mutants in memory, so tests that read source files as text see the original.

We wrote mutants to disk to measure the difference:

- All 4 `agent-connect-code.mjs` mutants were "killed" on disk by the verbatim-copy check in `agent-connect-code.test.mjs`. That kill would remove `agent-connect.test.mjs`'s unique kill on them, while the check proves nothing about behaviour.
- `pricing-single-source.test.mjs` killed 0 of the 42 `domain/billing.mjs` mutants on disk.

Serving mutants through a hook keeps source pins from getting credit for kills. A collector that writes files would reward them.

## Verdict

**Partly. The tests catch most faults where the code runs often, and miss them where it runs rarely.**

- **Permissions (78.7 %).** Every mutant in the common path (`resolveActor` for people and tokens, `authorize`, `canDelegate`) is killed, usually by many files. The survivors cluster in the rare branches: the delegation depth limit, an expired parent token, and the device and runner exemptions. 100 % line coverage hides all of these.
- **Agent connect (80.7 %).** One well-written file, `agent-connect.test.mjs`, holds 45 unique kills. The races (the claim, orphan-token revocation, concurrent polls) and the per-address guess limit are not tested.
- **Billing (62.7 % on a 20 % sample).** The pure engine is well tested. The ledger and service code that moves money has the most gaps:
  - the stale-`sent` re-send window
  - the dead-letter alert
  - a credit repaying the deficit
  - pagination at 100 entries
  - the balance emails
  - the checkout audit record

For Cupel, five things are now settled:

- Selecting tests by V8 block coverage is the right default: 3 to 4 files per mutant instead of 120 to 360.
- Serving mutants through a load hook works on a real suite: no file writes, safe in parallel, and source pins get no credit.
- Stopping a mutant after 2 killing files keeps unique kills exact and costs a third as much on hot code.
- A kill must be a reported failing test; a crash is an environment error.
- Mutation score is a different and lower signal than line coverage. It is worth the cost on critical modules: about 3 CPU-s per mutant when few files cover the code, about 40 CPU-s on hot code.

## D6 recommendation

**Use textual mutation with the zero-dependency lexer for v1. Do not add acorn now. Reject the TypeScript compiler API.**

- **Accuracy.** On Assay, the lexer agrees with acorn on every token (2 M tokens) and on 99.85 % of mutation sites, with no false sites. 0 % of mutants were invalid. The validity filter (`vm.SourceTextModule`, standard library) catches anything the lexer gets wrong, at about 0.2 ms per mutant.
- **Cost.** It is about 500 lines (the lexer and the operators) with no dependency, deterministic, and as fast as acorn.
- **What a pinned acorn would cost.** Version 8.19.0 is MIT-licensed, one 235 KB ESM file, with no dependencies of its own. It would be pinned exactly, justified in DECISIONS.md, and either vendored or installed. It buys:
  - ternary-condition mutants (the one large family a lexer cannot bound well)
  - exact unary or binary detection
  - statements that start with `(`

  It does not buy validity, which the filter already gives. Revisit if the ternary operator family is wanted, or for JSX.
- **TypeScript compiler API.** The local copy is TypeScript 7.0.2: a 30 MB package plus a 26 MB native binary for each platform, with its JS API under `unstable/` and run over IPC to a Go process. That is too heavy and too unstable for a pinned dependency.
- **TypeScript suites** (the Vitest forks). Node's built-in `module.stripTypeScriptTypes` (experimental) replaces types with spaces and keeps offsets, so the lexer can run on the stripped text and the edits map back unchanged. JSX/TSX is the one case that would need a parser; decide when the first JSX target appears.

DECISIONS.md was not changed; the owner records D6.

## Caveats and what was not verified

- **Contended timings.** S1 and S2 ran at the same time, with load averages of 16 to 68. Rates without contention were not measured.
- **Environment incident.** At 14:03:09 local time, a Homebrew upgrade of simdjson broke `node` (a dyld error, exit 134) until about 14:03:55.
  - The main runs had ended at 14:03:13.
  - An audit of the 412 results found no run with exit 134, and no counted kill without a failing test inside that window.
  - Two kills outside the window had no failing test. They were the `agent-connect-cli` file exiting 1 after about 28 s on the 2 infinite-loop mutants. Under the strict rule they are now counted as timeouts, not kills.
  - The first recheck (14:03:47) started inside the window: all 5 of its mutants came back as false kills. They were discarded and re-run at 14:05: 5 mutants, 27 file runs, all survived.
  - The runner now checks a known-good file before it starts, counts a kill only when a test is reported failing, and marks crashes as environment errors to re-run.
- **Billing is a sample.** It is 150 of 730 eligible mutants (seed 20261021). permissions and agent-connect are complete.
- **Permissions kill counts are partial.** Because of the stop-after-2 rule, its killing-test counts are incomplete. Its unique kills are exact.
- **Survivor classes are judged by reading the code.** No killing test was written to confirm any of them.
- **Per-test names.** They are rebuilt from `test:start` nesting. A file that runs tests concurrently could mislabel them; this was not checked across the suite.
- **Selection relies on one coverage run per file.** A test that reaches a block only sometimes may not be selected, which would understate kills. This was not measured.
- **The hook reaches child processes through `NODE_OPTIONS`.** A test that starts a child with a clean environment would run unmutated code there. The hook confirmed the mutant loaded for every mutant run, but not in every child process.
- **The lexer was checked against Assay's own code style** (semicolons everywhere). Code that relies on automatic semicolon insertion would lose remove-call sites, which need a `;`. The return-value end is found from `;` or a closing bracket.
- **Validity filter flag.** `vm.SourceTextModule` needs `--experimental-vm-modules`. `node --check` per mutant is the fallback (one process each).
- **Snapshot state checked without git.** git could not be run in the snapshot because this agent's harness blocks git outside its worktree. Instead, the 626 tracked files under `src/` were hashed and compared with `.git/index`:
  - 0 changed and 0 deleted
  - 2 untracked: `src/domain/pins.mjs` and `src/api/legal-pages.mjs`, which are git-ignored generated files
  - The six target files match their SHA-256 values taken before any run

  Only file mode wrote to `src/`: `agent-connect-code.mjs` 4 times and `domain/billing.mjs` 42 times, each restored at once and checked.
- **Snapshot status: clean.** The reviewer later ran `git -C .scratch/assay-s3 status --short`, and it printed nothing.
- **Not used.** The workerd suite, the Python suite and timings without contention.
