# S2: Per-test coverage for node:test

**Verdict: go.** In-process takes at test boundaries (method B) give per-test coverage that matches one-process-per-test runs (method A) almost exactly. On the three files, B costs 1.36× a plain run and A costs 7.4×. B also ran the whole Assay suite (4,724 tests, 421 files) at about 1.4× wall time, and every test still passed.

**D7 recommendation:** make per-test coverage the v1 default for node:test, using method B. Keep per-file coverage as the fallback, and use method A only to re-check a few selected tests (details at the end).

## Question

Can Cupel get per-test coverage cheaply for node:test, rather than only per-file coverage? We compared two methods on three large Assay files:

- **A.** One process per test. Each test is selected with `--test-name-pattern` and its coverage comes from `NODE_V8_COVERAGE`.
- **B.** One process per file. A preload connects `node:inspector` to the same process and calls `Profiler.takePreciseCoverage` at every test boundary.

## Method

### Line rule (`plans/spikes/s2/lines.mjs`, the same for both methods)

1. V8 ranges are nested. A character's count is the count of the innermost range that contains it. A character outside every reported range counts 0.
2. A line is covered when at least one code character on it has a count above 0. Code characters are the characters that are not whitespace and not inside a comment. Strings, template literals and regex literals count as code.
3. Lines with no code characters (blank lines and comment-only lines) are never counted.
4. Only files under `src/**` and `public/**` are counted. Query strings are dropped from module URLs.

A small scanner, not a parser, decides what is a comment. Over `src/` and `public/` it finds 174,157 code lines, against 174,110 from a naive "not blank, not `//`, not `/*`" count.

The range flattening runs in linear time after one sort. Turning one test's coverage into lines takes 0.4–17 ms.

### Method A (`run-a.mjs`)

- Lists each file's top-level tests with a one-line-per-test reporter (`reporter.mjs`).
- Runs `NODE_V8_COVERAGE=<dir> node --test-name-pattern="^<escaped name>$" <file>` once per test. This is a direct run, with no `--test` parent process.
- Runs the file once more with the pattern `(?!)`, which matches no test. That run gives the file's module-load coverage.
- Checks every run: exactly one test ran and passed. All 366 per-test runs (122 tests × 3 repeats) passed that check.
- Node processes that a test spawns inherit `NODE_V8_COVERAGE`, so A also sees their coverage.

### Method B (`hook.mjs`, run as `node --test --import hook.mjs <file>`)

**The inspector session.** `new inspector.Session().connect()` connects to the same process. It opens no port or socket, and `inspector.open()` is never called. Every run recorded `inspector.url() === undefined`. The hook then calls `Profiler.enable` and `Profiler.startPreciseCoverage({ callCount: true, detailed: true })` before the test file is imported. The in-process session answers `post()` synchronously; the hook checks this, so every checkpoint lands exactly at its boundary.

**Reset semantics** (`check-reset.mjs`): `takePreciseCoverage` does reset the counters in this mode.
- Each take returns only what ran since the previous take.
- Functions that did not run are left out.
- An async function that resumes after a take is reported with function count 0 and a block count above 0 for the code after the `await`. The innermost-range rule handles this correctly.

**Hooks.** The preload registers root-level `before`, `beforeEach` and `afterEach` hooks from `node:test`. Root hooks from a preload apply to every test in the file, nested ones included. Under `node --test`, the `--import` is passed on to each file's child process, so the method works with the runner's normal process-per-file isolation and its parallelism across files. No `--test-isolation=none` is needed.

**Where each segment's coverage goes.** A checkpoint is taken at every `beforeEach`. The closing checkpoint is a `t.after()` that our `afterEach` registers, which makes it run last. Each delta between two checkpoints is assigned like this:

| What ran | Goes to |
|---|---|
| Module load and the file's root `before` | **setup** |
| The file's `beforeEach`, `afterEach` and `t.after` | the test |
| A parent test's own code between its subtests | the parent |
| A subtest | the leaf test |
| Two or more leaf tests running at once | every one of them, with the segment marked **shared** |
| Anything between tests | **between** |
| Anything after the last test | **teardown** |

Two details about hook order:
- An `afterEach` registered later, from the root `before`, never runs.
- The file's own `afterEach` runs after ours. That is why the closing checkpoint uses `t.after()`.

**Child processes.** The hook wraps `child_process` (spawn, exec, execFile, fork and their sync forms) and `worker_threads.Worker`, so the number of processes each test starts is counted.

`demo-attribution.mjs` runs a synthetic file that exercises all of the cases above:
- File hooks land in the test.
- Nested subtests attribute to the leaf.
- Concurrent subtests produce a shared segment.
- A timer leaked by test `one` fires during test `parent` and is attributed to `parent`.
- A `spawnSync(node)` is counted.

### Definitions used in the tables

- **M(T):** the lines that method M attributes to test T.
- **Unique lines of T:** lines in M(T) that no other test of the three files covers and that are not setup lines of any file. In other words, the lines that would lose coverage if T were deleted.
- **Jaccard raw:** A(T) compared with setup ∪ B(T).
- **Jaccard test-only:** both sides with all setup lines removed.
- **Plain run:** `node --test <file>`.

**Repeat stability.** Comparing repeat 1 with repeats 2 and 3, A's line sets were identical for 244 of 244 test pairs and B's for 243 of 244.

**Where A and B disagree: first touch.** B never gave a test a line that A's own run of that test missed. In the other direction, A covered 3,616 lines across 62 tests (51 in drop-in, 11 in fanout) that B gave to an earlier test. These are lazy initialisation and caches that only the first test to reach them pays for in a shared process.

This changes unique lines in 3 drop-in tests:
- 74 lines are unique under B only.
- One test flips from zero unique lines (A) to 25 (B).

Here the bias was almost always in the safe direction for advice: it makes B call a test valuable when it is not, rather than calling a valuable test worthless. The exception was one line in one fanout test, unique under A but not under B; that test still had 11 unique lines under B, so its verdict did not change. Leaked async work, however, can move lines away from the test that owns them (see "Concurrency" below).

**Overhead.** B/plain wall time per paired repeat was 1.48×, 1.56× and 1.39×. Plain repeat 3 had one failure (`demo-workspace`: "the bundle is deterministic"), which looks like load-related flakiness; it passed under B.

**Where the extra 172 s of CPU went:**

| Part | CPU, s | Per test, ms |
|---|---:|---:|
| Takes (10,709 takes) | 55 | 5.1 per take |
| In-process conversion to lines at exit | 71 | about 15 |

The conversion was not optimised. It re-scans every source in every process. The output was 45.7 MB of line sets.

**Attribution checks:**
- 4,723 tests were seen by the hook. The missing one is skipped, so its hooks do not run.
- 2 tests are nested (inside `describe`).
- 0 segments were shared: no file runs its tests concurrently.
- 3 between-test segments held leaked async work: `queue-time` (29 and 681 lines) and `right-sizing` (570 lines).

**Child processes:**
- 184 tests in 45 files start a child process.
- Only 46 tests in 16 files start a node process (`node`, `cri`, worker), whose src coverage B cannot see.
- The rest start git, python3, tar or a shell, which have no JS coverage under either method.
- None of the 122 tests in the three files spawns anything.

**Unique lines across the whole suite (B):**
- Per test: 21,430 unique lines, and 2,761 of 4,723 tests (58%) have zero unique lines.
- Per file: 43,533 unique lines, and 46 of 421 files have zero unique lines.
- S1 owns the per-file numbers; these are only a cross-check, and they carry B's first-touch bias.

**Rough cost of A on the whole suite.** A's 7.4–7.9× on the three files would put it at roughly 45 min of CPU, or 4–5 min wall on 12 cores. B costs about 1.4× the plain run.

## Answers to the attribution questions

- **Nested subtests.** Attribute to the leaf. A parent keeps only the code it runs outside its subtests. Roll up to the top-level test where a test must be addressable by `--test-name-pattern` (A, re-runs). Both views come from the same data.
- **Concurrency.** Overlapping tests are detectable: two leaves are active at one checkpoint. Their segments are marked shared and go to every owner, and Cupel should not count shared lines as unique. Assay has none. One case is not detectable: async work that a finished test leaves behind and that fires inside a later test. That work goes to the later test, as `demo-attribution.mjs` shows. Leaked work that fires between tests is caught as "between" (3 cases in Assay).
- **Hooks and module load.** Module load and root `before` go to setup. `beforeEach`, `afterEach` and `t.after` go to the test. Uniqueness subtracts every file's setup lines.
- **Child processes.** B cannot see them. In Assay, 46 tests (1%) start node processes. Cupel should flag these tests ("coverage partial: spawns node") and either use A for them or leave them out of retire advice.
- **Reset.** Confirmed. Each take is a delta.

## Node versions (Cupel must support 22+)

Only Node 26.7.0 was run. From the Node docs, not verified here:

| Feature | Since |
|---|---|
| `node:inspector` `Session.connect()` | 8 |
| `--import` | 20.6 / 18.18 |
| `t.after()` | 18.13 / 19.3 |
| Custom reporters and `--test-reporter-destination` | 18.15 / 19.6 |
| `--test-name-pattern` | 18.11 |
| `TestContext.fullName` | 22.3 |
| `TestContext.filePath` | 22.6 |

`fullName` and `filePath` have fallbacks: `name` and `process.argv[1]`.

These need checking on 22.x:
- that root-level hooks registered from an `--import` preload apply to the file's tests;
- that `--import` reaches each file's child process under `node --test`;
- that a `t.after()` registered from `afterEach` runs last.

Assay itself requires Node 22.16 or later.

## D7 recommendation

**Per-test coverage is the v1 default for node:test, through method B.** It costs about 1.2–1.7× a plain run (median 1.36× on the three files and about 1.4× on the whole suite under load), needs no change to the user's tests, opens no port, and agrees with per-process ground truth on 121 of 122 zero-unique verdicts.

- **Per-file stays** as the fallback when the hook cannot attach (a runner without per-test hooks, or an unsupported Node version) and as the report's summary level.
- **Method A is not a default.** At 4–11× it is too slow for a whole suite. Use it only to re-check a short list of tests: retire candidates before advice is shown, and tests flagged as spawning node processes. That removes B's first-touch bias and child-process blind spot where they matter.
- **Before the build:** make line conversion cheap (cache source analysis across processes, or convert once in the parent), store line sets compactly, and test the hook on Node 22.x in CI.

## Caveats and what was not verified

- **Not tested on Node 22.** Only 26.7.0 was available. The version table above comes from the docs.
- **Contended timings.** All timings ran while S1 and S3 were running. The spread between repeats is up to about 40% on wall time (for example, plain suite wall ranged from 41 to 53 s), so the ratios are good to roughly ±0.2.
- **Uniqueness covers only three files.** In the tables, uniqueness is counted across these three files only. Against the whole suite, many of these tests' unique lines would be covered elsewhere. The whole-suite figures come from B only.
- **No concurrency or nesting in the measured files.** The three files have none, so A versus B was not compared on concurrent or nested tests. Those cases were checked only with the synthetic demo and the whole-suite run (2 nested tests, 0 concurrent).
- **Line rule artefact.** A line such as `export function f() {` counts as covered at module load, because `export` sits outside the function's range. This applies to both methods equally, and such lines fall into setup, never into unique lines. The comment scanner is heuristic: regex-versus-division is decided from the previous token.
- **Coverage scope.** Only line coverage was measured, not branch coverage.
- **A's run style.** A ran tests directly (`node file`), not under `node --test`, which would add one more process per test. A selects top-level tests only.
- **Partial whole-suite comparison.** The whole-suite run compared B with plain only, not with A.
