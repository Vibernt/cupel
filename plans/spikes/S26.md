# S26 — Jest and Vitest selective profile feasibility

Date: 2026-10-25. Status: concluded feasibility probe; implementation and selective acceptance remain open. This spike changes no product code or published capability.

## Decision-complete probe plan

1. Use only the pinned, installed Jest 30.2.0 fixture and Vitest 4.1.11/5.0.1 runtimes. Copy test fixtures into ignored scratch directories; link existing dependency trees read-only. Do not install packages, modify CodeCrystal, read private inputs, or switch Jest/Vitest modes automatically.
2. Run ordinary fixture startup and inspect the exact installed runtime paths for module execution, transforms, worker/fork creation, and test lifecycle. Preserve each fixture's own config and source text. Record command, runtime version, test count, exit, and only bounded diagnostics.
3. Probe the current `node-readonly-files-v1` profile's VM, dynamic compiler, child and worker denials with controlled scratch subjects. Relate each denial to an actual Jest/Vitest call site. An early denial is a blocker for that existing profile, not proof a new profile is safe.
4. Define a separate, opt-in profile only if a finite contract can pin the framework version, project config, transform implementation, worker topology, dependency bytes, and runtime. The boundary must distinguish trusted framework/compiler work from untrusted test/source callbacks before any file or built-in I/O; log all setup/transform imports, reads and probes; deny source-origin VM, dynamic code, child/worker, native and network channels; retain complete per-test setup/teardown/concurrent ownership and ordinary-result parity. Any unproved channel refuses before selection. Do not substitute `runInBand`, `--no-isolate`, a different pool, or a different transform without a separately named, approved execution contract.
5. Acceptance for a future implementation requires actual negative probes for source text, cached constants, captured aliases, asynchronous/descriptor/stream I/O, missing-path and directory probes, VM and dynamic compiler escape, test-created process/thread, transform-only inputs, shared state, incomplete sidecars, per-test and concurrent coverage, and base/head snapshot drift. Then replay the S12 faults and a real scratch change with zero false greens and at least one genuine selective decision. Slower but correct is allowed; an all-refusal profile is not complete. Until these gates pass, mark Jest/Vitest selective mode unsupported and keep full guard authoritative.

## Prior evidence

S12b's JS pilot observed passing ordinary and fresh-process file runs for Jest 30.2.0 and Vitest 4.1.11, but it did not establish complete observation channels, per-test results/setup parity, or ordinary isolation equivalence. Its sidecars remained unsupported. The current Node profile explicitly blocks `node:vm`, child processes and workers, and custom transforms; this spike tests the consequence against actual framework paths.

## Actual-runtime method and observations

The reproducible smoke scripts in [`s26-framework-profiles/`](s26-framework-profiles/) copy only the existing fixture's named source, test and config files into ignored `.scratch/s26-framework-profiles/`; they link installed dependencies read-only and set a minimal environment. `probe.mjs` uses the project's ordinary command: Jest with its own `maxWorkers: 1` config and **without** an added `--runInBand`; Vitest with its own config and default pool. `trace.mjs` adds a call-counter preload that records API names and PIDs, never source text. `negative.mjs` exercises scratch-only representative subjects under the current Node profile. All three scripts assert their expected outputs and exited zero. No installation, CodeCrystal write, network probe, product change or secrets read was made.

|---|---|---|---|
| Jest 30.2.0 | 2 suites, 8 tests passed | 2 suites, 8 tests passed | `vm.compileFunction` 280, `vm.createContext` 2, `vm.runInContext` 4; one traced process |
| Vitest 4.1.11 | 1 file, 4 tests passed | 1 file, 4 tests passed | `child_process.fork` 1 in parent; `vm.runInThisContext` 2 in worker; two traced processes |
| Vitest 5.0.1 | 1 file, 4 tests passed | 1 file, 4 tests passed | `child_process.fork` 1 in parent; `vm.runInThisContext` 2 in worker; two traced processes |

The installed source explains those calls. Jest `jest-environment-node/build/index.js` creates and enters a VM context (lines 105–106); `jest-runtime/build/index.js` reads and transforms module source (lines 1243–1304), then compiles it in that context (lines 1311–1324). `@jest/transform/build/index.js` invokes the project's transformer and may read its own transform cache (lines 396–535). The fixture's `transform.cjs` invokes TypeScript 5.9.3. Vitest 4's installed `cli-api.CnMVyzaz.js` forks its `workers/forks.js` entry (near line 3151), while Vitest 5's `index.DzobfTyw.js` does so near line 11026; their default pool is `forks` (Vitest 5 near line 14310). Both versions' `module-evaluator.js` execute Vite-supplied transformed module text with `vm.runInThisContext` (Vitest 4 near line 206, Vitest 5 near line 258), and the parent calls Vite `transformRequest` (`cli-api.CnMVyzaz.js` near line 415; `index.DzobfTyw.js` near line 6888). The preload's actual calls establish execution on this fixture; these source paths identify where a future privilege boundary would need to attach.

The current Node profile **cannot** run these paths. Its `modules.cjs` blocks `node:vm`, `node:child_process` and `node:worker_threads`, and `bootstrap.cjs` blocks subject-created `Function` constructors. On Node 26, four controlled scratch subjects exited 1 and recorded persistent denials: VM, fork and worker requests as `forbidden-module`, dynamic compiler as `forbidden-Function`. On Node 22, the current profile exited 9 **before bootstrap** because its required `--allow-inspector` flag is unavailable (`bad option: --allow-inspector`); no Node 22 denial or selective safety claim follows from that startup failure. The actual framework runs above were ordinary, outside this profile. `negative.mjs` retains bounded output and event traces for audit.

The fixture's single-process Jest trace is specific to its `maxWorkers: 1` config and small inventory. It does not justify forcing `--runInBand` on a different project. Cupel's existing Jest collector itself uses `--runInBand` (`collect/jest/process.mjs` lines 69, 88), and the Vitest collector uses `--pool=forks` (`collect/vitest/index.mjs` line 116); a selective profile must bind those as **named execution policies** and prove parity with that project's ordinary full run. Neither switch is an automatic substitute for an unsupported project configuration.

## Boundary required before selective execution

**Jest 30.2.0 profile.** A trusted launcher must pin Jest, circus, environment, transformer, TypeScript (when configured), Node, project config and dependency bytes. It must establish the read-only/declared-input boundary before Jest config, setup, or transformer code executes. The VM context and `jest-runtime` compiler may receive a narrowly authenticated capability to compile only the transformed module whose original path, source hash, transformed hash, source map and importer are recorded. The project test/setup/transform callback must not inherit general VM, dynamic compiler, process/thread, native or network privileges. Instrument Jest's module resolver, `readFile` caches, transformer and VM built-in handoff: Node loader hooks alone do not see every Jest VM import. Record config/transform reads and failed probes globally or under an exact file owner; preserve on-disk source reads so text pins see pristine bytes. Before any test callback, guard the VM's built-ins and filesystem aliases, including `fs` passed by Jest's `_requireCoreModule`. Prove circus event completion, `beforeEach`/`afterEach` and `beforeAll`/`afterAll` attribution, exact selected-row identity and overlapping concurrent ownership (the fixture has two concurrent tests). Unsupported custom environments/runners/transformers, ESM VM modes, mocks or child/worker paths must be refused unless independently pinned and probed.

**Vitest 4.1.11 and 5.0.1 profiles.** Pin the exact Vitest/Vite pair, config, plugins/transforms, Node, `forks` pool and `isolate: true` when those are the project's ordinary modes. Permit only the framework-owned fork of its known worker entry, argument/env/IPC shape and private outputs; preload the worker guard before transformed test code. Deny subject-created forks, threads and direct VM calls. The parent Vite server must record `transformRequest` inputs and every plugin/config read/probe with the Vite module graph's importer and transformed hash. The worker must bind each `fetchModule`/resolve RPC result to that graph before `VitestModuleEvaluator` compiles it, while separately observing native/external modules and all filesystem channels in both processes. Trust cannot be inferred from a call stack alone: transform plugins and mocks can invoke the same framework methods on user-controlled inputs. The existing Vitest setup hook records per-test V8 coverage with `beforeEach`, `afterEach` and `onTestFinished`, but a selective profile still needs an independently complete proof for setup/afterAll, selected rows, concurrent overlap, child completion and ordinary-result parity. Browser, VM pools, threads, non-isolated execution and custom transforms require separate contracts and are refused here.

**Shared refusal gate.** Source/transform/config or dependency identity drift; missing owner or pretest observations; a missing child/VM trace; new native/IPC/network/custom loader activity; ordinary/profile result or setup disagreement; a source pin kill; or incomplete per-test/concurrent coverage must prevent selection. Refusal must occur before a partial head can be treated as a full guard result. Node 22 needs a separately proven inspector/permission strategy; changing flags silently would change the profile. Allowing framework VM/fork work through a finite privilege bridge is a new execution boundary, not a relaxation of `node-readonly-files-v1`.

## Verdict and next gate

**Feasible architecture identified, selective capability unproved.** The current profile predictably refuses required framework operations and Node 22 fails at startup. The six ordinary framework runs and six traced runs show the exact VM/fork/transform execution paths, but no trusted VM/transform bridge, complete pretest filesystem observation, per-test profile parity, S12 fault replay, or useful selective decision was implemented or tested. The next best action is to implement a *separate* opt-in Jest 30.2.0 profile on Node 26 first, with the VM and transform bridge plus source-pin/concurrent negative controls. Vitest then needs its two-process Vite/worker bridge for each pinned version. Neither is ready for CLI/MCP promotion. If the owner prefers not to grant those narrowly scoped framework capabilities, the correct outcome is an explicit unsupported result; the spike did not choose or apply another execution mode.
