# S9: Does local git history make Cupel's advice more credible?

## Question

S6 found that coverage-based retire advice was wrong 19 times in 20, mostly because tests that share lines assert different things, and that consolidating same-shape siblings works (8 of 11 correct). Can local git history fix the first or support the second? Four hypotheses:

- **H1, fix commits.** Tests first added in a bug-fix commit are regression tests, so history could protect the tests S6 wrongly flagged for retirement.
- **H2, batches.** Tests added together in one commit, especially by an agent, are near-duplicates, so history could support consolidation.
- **H3, co-change.** Tests whose lines change with copy, CSS or doc changes, but rarely with logic, are brittle pins.
- **H4, cost.** What does reading the history cost?

Constraint for any spec change: git signals may only raise protection or support consolidation. They never justify retire on their own.

## Answer in brief

**No. Local history does not make the advice more credible on these two suites, so the spec should not add history fields.**

| Hypothesis | Verdict | Key numbers |
|---|---|---|
| H1 fix commits | **Rejected** | Retire candidates come from fix commits at the suite's base rate: Assay 5.8 % against 6.1 %, CodeCrystal 28.1 % against 28.9 % (subject match; p 0.79 and 0.91). Of the 26 retires S6 judged wrong or debatable, none came from a small fix commit (5 tests or fewer). Fix commits that add a few regression tests add only 0.6 % of Assay's tests and 0.3 % of CodeCrystal's |
| H2 batches | **Rejected as evidence** (consistent, but it does not discriminate) | All 12 same-shape clusters, including the 6 judged correct, were added in one commit. But 70 % (Assay) and 67 % (CodeCrystal) of all same-file pairs were too, and so were 20 of the 20 consolidations S6 judged wrong. 99.6 % of Assay's commits carry a Claude trailer |
| H3 co-change | **Weak, confounded, not usable** | Assay: pinned tests were later edited in a console-page commit with no logic change more often than other tests (12.8 % against 2.5 %). Within UI test files only, the rates are 21.6 % against 13.3 % (p 0.03). Among the hand-checked pins, 2 of 8 correct and 0 of 11 wrong (p 0.16). 86 % of tests were never edited after they were added. CodeCrystal has no signal |
| H4 cost | Cheap to read, often unavailable | Parsing the exports takes 1.0 s (Assay) and 0.3 s (CodeCrystal). Live, on a replayed repository of Assay's shape: `git blame` of 461 test files takes 18 s, or 4 s with 8 in parallel, and `git log --numstat` takes 2.5 to 10 s, on a machine at load 140 to 180. A depth-1 CI checkout (GitHub's default) loses everything; at depth 50, 75 % of Assay's tests and 83 % of CodeCrystal's lie beyond the boundary |

**Why it fails.** In these agent-written histories, tests arrive in large batches with feature commits: a median of 16 (Assay) and 21 (CodeCrystal) tests per introducing commit. Commit messages name fixes in bulk ("fix(bench): restore tracked context efficiency harness" added 131 tests), and the product vocabulary overlaps with fix words (Assay is a CI product: "flake quarantine", "duration regressions", "Assign fix"). So no history signal tells a regression test from a feature test, or a good merge from a bad one, at the unit of advice.

## Data and method

### Data (read-only)

| | Assay | CodeCrystal |
|---|---|---|
| HEAD | 5a5a1313 (`.scratch/assay-base`) | 09fc900 (`.scratch/cc-s6`) |
| Commits in the export | 982, of which 310 merges; 1 root (an import) | 917, of which 140 merges; 1 root |
| Test files blamed | 462 exported, 421 with S6 tests | 176 exported, 173 with S6 tests |
| S6 units mapped (sites) | 4,294 of 4,294 | 1,191 of 1,191 |

A **site** is one test definition: its file and the line of its title (`test(`, `it(` or `def test_…`), taken from S6's strict detector (`brittle-strict.json`: `line`, `endLine`, masked shape). Rows of a parametrized test share a site, which is S6's unit of advice. All counts below are in sites.

The S6 inputs are the reports `report-v0.json` and `report-v1.json`, the inputs, and the hand-checks (`handcheck-*.json`, `judgements.json`).

### Mapping a test to its introducing commit

The introducing commit is the blame commit of the title line. Each mapping is checked four ways:

| Check | Assay | CodeCrystal |
|---|---|---|
| moved: blame followed a rename (its filename differs from the path) | 19 | 0 |
| title-newer: some body line is older than the title line (title edited later, or the body came from elsewhere) | 127 | 25 |
| possible-move: the commit is the path's first in the `--no-renames` log and deletes at least the test's length from another test file (a split or move that blame did not follow) | 170 | 78 |
| not in the exported log | 0 | 0 |
| **ambiguous** (title-newer, possible-move or not in log) | **296 (6.9 %)** | **103 (8.6 %)** |
| from the root import commit (no real origin) | 79 (1.8 %) | 0 |

The results below use the title-line commit. Re-running H1 with the oldest body-line commit, or without the ambiguous sites, moves the retire-group rates by at most 4 points and changes no conclusion (`results/h1.json`, `sensitivity`). CodeCrystal's critical group moves the most, from 52 % to 46 %.

### Fix commits: the regex and its precision

Fix commit regex, case-insensitive, whole words, matched against the subject, or against the subject and body:

```
\b(?:fix(?:e[sd]|ing|up)?|bug(?:s|fix(?:es)?)?|regress(?:ion|ions|ed|es)?|revert(?:s|ed)?|hotfix(?:es)?|crash(?:es|ed)?|flak(?:e|es|ed|y|iness))\b|\[fault:|\b(?:close[sd]?|resolve[sd]?)\s+#\d+|\bGH-\d+\b
```

The root commit of each history is an import and never counts as a fix. Assay's root subject says "fix runner portability", but the commit imports 79 tests.

| Non-merge commits | Assay | CodeCrystal |
|---|---|---|
| total | 672 | 777 |
| subject or body matches | 112 (16.7 %) | 90 (11.6 %) |
| subject matches | 38 (5.7 %) | 45 (5.8 %) |

**Precision.** I read and judged the following samples (seeded, `fixre.mjs`), marking each commit fix, partly a fix, or not a fix:

- 30 commits the regex matches and 30 it does not, 15 of each per suite;
- 20 more subject matches, 10 per suite.

| Sample | n | fix | partly | not | strict | lenient |
|---|---|---|---|---|---|---|
| matches, subject or body | 30 | 13 | 7 | 10 | 43 % | 67 % |
| of which body only | 22 | 6 | 7 | 9 | 27 % | 59 % |
| matches in the subject (both samples) | 28 | 18 | 6 | 4 | **64 %** | **86 %** |
| non-matches | 30 | 2 | 3 | 25 | (miss rate 7 % / 17 %) | |

- Body matches are mostly feature prose: "flaky and quarantined tests", "mode: fixed", "bug classes", "reverts on failure".
- Recall is low, especially on Assay. Its fix commits often describe the behaviour without a fix word ("Open the Quality project page on its overview…": the page was blank). The estimated recall of the broad regex is about 31 % on Assay and 59 % on CodeCrystal. For the subject-only regex it is roughly 15 % and 35 %.
- Every judgement is from one reader, from the subject and body only.

**Small fix.** A subject-matching fix commit that introduced at most 5 test sites. It approximates "a fix with its regression test" and excludes bulk commits that only name a fix.

### Other definitions

- **Agent commit:** the body has a `Co-Authored-By:` trailer naming Claude, Anthropic, Codex, OpenAI, Cursor, Copilot, Devin, Aider, Gemini, Jules, Windsurf, Cline, Amp, Sweep, Codegen, ChatGPT or GPT-n.
- **Batch size:** the number of sites whose introducing commit is that commit.
- **Same shape:** the Jaccard similarity of S6's masked-body 4-token shingles, as in S6's engine.
- **Commit kind (H3)**, from the commit's non-test files:
  - `logic`: any non-UI code file;
  - `ui`: console or web page code (`public/`, `web/`) and no logic file;
  - `presentation`: only docs, CSS or HTML;
  - `data`;
  - `test-only`.
- **A test's later edits:** the blame commits of its body lines, other than its introducing commit. Blame shows only the last commit to touch each line, so edits that were later overwritten are not seen.
- **Statistics:** two-sided Fisher exact tests for a group against the rest of the suite, and one-sided binomial tests for a small judged set against the suite's base rate. Samples of 10 to 20 are reported, but conclusions are drawn only where the numbers allow it.

## Results

### H1: are wrongly flagged retire candidates regression tests?

**Populations** (no hand judgement), share of sites whose introducing commit is a fix commit, with p against the rest of the suite:

| Assay (4,294 sites) | n | fix, subject | fix, subject or body | small fix | p (subject) |
|---|---|---|---|---|---|
| all units (base rate) | 4,294 | 6.1 % | 22.1 % | 0.6 % | |
| v0 retire advice (coverage only) | 669 | 5.8 % | 21.2 % | 0.7 % | 0.79 |
| v1 "unverified retire" (kept, marked) | 938 | 6.4 % | 23.3 % | 0.4 % | 0.70 |
| v1 keep: has a unique line | 1,973 | 6.8 % | 23.9 % | 0.4 % | 0.11 |
| v1 critical | 2,166 | 5.5 % | 19.3 % | 0.5 % | 0.10 |

| CodeCrystal (1,191 sites) | n | fix, subject | fix, subject or body | small fix | p (subject) |
|---|---|---|---|---|---|
| all units (base rate) | 1,191 | 28.9 % | 36.4 % | 0.3 % | |
| v0 retire advice | 96 | 28.1 % | 35.4 % | 0 % | 0.91 |
| v1 unverified retire | 370 | 24.9 % | 35.4 % | 0.3 % | 0.045 (lower) |
| v1 keep: has a unique line | 670 | 28.8 % | 33.3 % | 0.4 % | 0.95 |
| v1 critical | 128 | 52.3 % | 62.5 % | 0 % | <0.001 |

- Retire candidates are not enriched for fix commits under any definition. CodeCrystal's unverified-retire group is slightly *less* often from fix commits.
- CodeCrystal's high base rate comes from four bulk commits that match the regex: "fix(bench): restore tracked context efficiency harness" (131 tests restored), "Track the V7 value study … and the briefing-capture fix" (98), "Companion GitHub publication: fixes from the delivery-pipeline audit" (36) and "Fix indexing of real repositories…" (34). Its critical tests are fix-rich for the same reason: the harness tests are budget and isolation tests.
- Assay's fix-subject sites are mostly feature commits whose names use fix words: "flake quarantine", "duration regressions", "Assign fix".

**Hand-checked retire suggestions** (S6 v0, plus CodeCrystal's first draw; ids deduplicated):

| | n | fix, subject | fix, subject or body | small fix |
|---|---|---|---|---|
| Assay, wrong or debatable | 10 | 0 | 1 | 0 |
| Assay, correct | 0 | | | |
| CodeCrystal, wrong or debatable | 16 | 6 | 8 | 0 |
| CodeCrystal, correct | 1 | 0 | 0 | 0 |

- Against the base rate, Assay's 0 of 10 gives p 1.0 and CodeCrystal's 6 of 16 gives p 0.30 (one-sided binomial). Comparing wrong with correct is impossible, because only one suggestion was correct.
- CodeCrystal's 6 "fix" hits come from three bulk commits (131, 34 and 12 tests).
- One case reads as a true regression test. `test_warm_with_a_failed_refresh_gives_up_quietly_and_keeps_the_login` was added by "Companion audit fixes: keep the login on a transient refresh failure, …", a commit that adds 12 tests. S6 put this false positive down to a missed tier word. History would have caught 1 of 26, at the cost of also flagging every test in such batches.
- For S6's main cause, "assert" (unique assertions on shared lines; 6 Assay and 6 CodeCrystal items), the introducing commits are feature commits ("Add GitLab CI, CircleCI … Travis and Drone migrators", "Add Runs pages…") or bulk fix-named commits. History does not see assertions any more than coverage does.

**Verdict H1: rejected.** Fix-commit origin does not separate the tests a person would keep from the rest. Regression tests added alone with a fix are almost absent from these histories (24 and 4 sites).

### H2: are same-shape consolidation clusters added together?

| | Assay | CodeCrystal |
|---|---|---|
| same-file pairs of sites | 29,152 | 7,240 |
| added in one commit | **70.1 %** | **67.1 %** |
| pairs with shape ≥ 0.8 | 9, all in one commit | 11, all in one commit |
| p (shape ≥ 0.8 against other pairs) | 0.066 | 0.020 |
| P(shape ≥ 0.8 \| same commit) | 9 / 20,425 = 0.04 % | 11 / 4,860 = 0.2 % |
| S6 v1 same-shape clusters, in one commit | 2 / 2 | 10 / 10 |
| …of which judged correct, in one commit | 1 / 1 | 5 / 5 |
| …judged debatable, in one commit | 1 / 1 | 2 / 2 |
| S6 v0 "line subset" consolidations (all judged wrong or debatable), in one commit | 443 / 516 (86 %), judged 10 / 10 | 331 / 380 (87 %), judged 10 / 10 |
| median batch (sites per introducing commit), per site | 16 | 21 |
| sites in batches of 10 or more | 76 % | 64 % |
| non-merge commits with an agent trailer | 669 / 672 (99.6 %, all Claude) | 664 / 777 (85.5 %, all Claude) |
| sites from agent commits | 99.9 % | 65.7 % |

Pooled across both suites, the 6 correct clusters, all in one commit, against a base rate of about 0.69: one-sided p ≈ 0.1. The share of one-commit pairs rises with shape similarity (Assay: 69 % below 0.2, 84 % at 0.6 to 0.8, 100 % at 0.8 or more).

The 20 consolidation suggestions S6 judged wrong were also all added in one commit. The 0.8 shape threshold already picks only one-commit pairs.

**Verdict H2: rejected as evidence.** "Added together" is the normal state of a test file in agent-written suites, and it holds for wrong merges as often as for right ones. "Agent-authored" is close to a constant here: every trailer names Claude, and many of the CodeCrystal commits without one were probably written by agents too, judging by their style and branch names (`worktree-agent-…`). That was not verified. The history adds nothing that the shape rule does not already capture.

### H3: are tests that change with copy, CSS or docs brittle pins?

| Assay | pinned (S6 v1 strict detector) | not pinned | p |
|---|---|---|---|
| sites | 172 | 4,122 | |
| ever edited after being added (blame) | 51 (30 %) | 539 (13 %) | |
| edited in a presentation-only commit (docs, CSS, HTML) | 0 | 7 | |
| edited in a presentation or UI commit with no logic | 22 (12.8 %) | 103 (2.5 %) | 2e-9 |
| introduced in such a commit | 30 (17 %) | 298 (7 %) | 1e-5 |
| **UI test files only** (`tests/ui-*`): edited with UI, no logic | 22 / 102 (21.6 %) | 94 / 707 (13.3 %) | 0.034 |

| Hand-checked rewrites (pins only, slow rule excluded) | n | edited with presentation or UI | never edited with logic |
|---|---|---|---|
| Assay, correct (real pins) | 8 | 2 | 2 |
| Assay, wrong (detector errors) | 11 | 0 | 0 |
| Assay, debatable | 1 | 0 | 0 |
| CodeCrystal, correct | 4 | 0 | 0 |
| CodeCrystal, wrong | 2 | 0 | 0 |
| CodeCrystal, debatable | 5 | 0 | 0 |

- On Assay, the population association is mostly file type. UI tests are edited with console pages whether or not they pin anything.
- Inside UI files the difference is small (p 0.03), and as a pin finder the history signal is weak:
  - 22 of the 125 sites edited this way are pinned (18 % precision);
  - 22 of 172 pins are found (13 % recall).
- Among the judged rewrites it found 2 of 8 real pins and none of the 11 detector errors (Fisher p 0.16). That is too few to conclude anything.
- No edit was CSS- or doc-only. Assay's CSS pins read `tokens.css` and page source, but the tests were added with those files and never touched again.
- CodeCrystal: 7 pinned sites, none ever edited, and only 65 of 1,191 sites were edited at all. There is no signal.

**Verdict H3: weak and confounded, not usable.** The static detector (S6) finds pins directly. Co-change history mostly reports that a test is a UI test.

### H4: what does history cost?

| | Assay | CodeCrystal |
|---|---|---|
| parse the exported `git log --numstat` | 16 ms | 23 ms |
| parse the exported blame of every test file (110 k / 22 k lines) | 0.93 s | 0.12 s |
| map every site, all checks | 1.0 s | 0.3 s |
| **live, replayed repository** (`synth.mjs`): `git log --no-renames --numstat` | 10.0 s | 2.5 s |
| `git blame --line-porcelain` of every blamed test file, one at a time | 17.9 s (461 files, 39 ms each) | 6.0 s (176 files, 34 ms each) |
| the same, 8 at a time | 4.0 s | 1.1 s |
| most-changed file (Assay `drop-in.test.mjs`, 22 commits, 2,122 lines) | 50 ms | 56 ms (`test_retrieval.py`) |

- The replay applies each non-merge commit's numstat, oldest first, as one linear chain of synthetic text (672 and 777 commits; 114 k blamed lines against the real 110 k). Merges are dropped, so live blame on the real history, with 310 merges for Assay, will cost somewhat more.
- The machine was at load average 140 to 180 from other work, so these times are upper bounds for this machine and can be several times too high.
- Estimate at Assay's size: **about 5 to 20 s** of blame plus 1 to 10 s of log per full scan, once per commit. That is affordable beside a 50 s coverage run, and cacheable by blob id.

**What is lost under squash merges and shallow clones:**

| | Assay | CodeCrystal |
|---|---|---|
| merge commits | 310 of 982 (32 %) | 140 of 917 (15 %) |
| non-merge commits that look squashed ("(#n)" subject, or two or more `* ` subject lines in the body) | 1 of 672 (0.1 %) | 9 of 777 (1.2 %) |
| non-merge commits touching 20 or more files | 225 (33 %) | 115 (15 %) |
| commits that introduce 10 or more tests | 170 | 26 |
| **simulated squash merge**: sites whose introducing commit sits on a merged branch | 3,674 (86 %) | 291 (24 %) |
| introducing commits, before → after | 427 → 236 | 148 → 138 |
| median batch per site, before → after | 16 → 28 | 21 → 22 |
| sites from fix commits (subject or body), before → after (merge message only) | 950 → 746 | 434 → 358 |
| **shallow clone**: sites whose introducing commit lies beyond depth 1 / 10 / 50 / 100 / 200 | 100 % / 97 % / 75 % / 61 % / 19 % | 100 % / 99 % / 83 % / 73 % / 34 % |

Neither repository squash-merges today: they use merge commits, and their commits are already large. A squash workflow would fold most of Assay's history into PR-sized commits and make batches larger still. In a shallow clone, blame attributes every older line to the boundary commit. `actions/checkout` defaults to depth 1, so in the GitHub Action, where the guard runs (L5), history is absent unless `fetch-depth: 0` is set.

## Recommendation for the spec

**Do not add history fields to `cupel-spec/1`.** Each candidate rule fails on this evidence:

| Candidate field | Rule it would feed | Why not |
|---|---|---|
| `tests[].history.addedInFix` | Protect (no retire, a `regression-test` reason) | Not enriched among wrongly flagged retires (H1). The regex is 64 % strict, 86 % lenient precise on subjects, with low recall. At test level it is dominated by bulk commits |
| `tests[].history.batchSize`, `addedIn` | Support consolidation of same-shape pairs added together | True of 67 to 70 % of all same-file pairs and of every wrong consolidation judged (H2). It adds no information to the shape rule |
| `tests[].history.agentAuthored` | Lower confidence, or support consolidation | 86 to 100 % of commits; constant within a suite (H2). A trailer is self-reported and easy to drop |
| `tests[].history.coChange` | Support rewrite, or mark a pin | Confounded with UI test files; 18 % precision as a pin finder (H3). The detector is better |

Adding them would cost a collector obligation (blame per test, rename handling, a depth check), a dependency on CI checkout depth, and a non-hermetic input. Determinism holds only for a fixed history. None of the four would change a judged outcome for the better.

What to do instead:

1. **Keep D5 as it is.** Retire needs targeted mutation or a near-duplicate body. History cannot stand in for either: it sees assertions no better than coverage does (H1).
2. **Let people mark regression tests through the existing T1 tags.** A team that adds a `critical` tag, or a title word it configures (`tiers.extraTitleWords`, for example `regression`, or a fault-id pattern), gets the protection H1 hoped for, and the history stays out of the engine. Assay titles already carry such notes ("negative: before 0.4.8 they came back"). Whether title words are precise enough was not measured here.
3. **If history returns later** (Vibernt Assay's run history, which knows which tests actually caught regressions, is the stronger signal; PRODUCT.md assigns history to Assay), add it as one optional field with a protection-only rule. For example, `tests[].history: { caughtRegression: true }` would give keep with reason `caught-regression`, would never feed retire or consolidate, and would be ignored when absent. Only evidence of an observed failure qualifies, not commit wording.
4. **Collector guidance, for anyone who adds history anyway:** refuse shallow clones (`git rev-parse --is-shallow-repository`), follow renames, treat the root and import commits as unknown, and report ambiguity.

## Caveats and what was not verified

- **Two suites, one author's style.** Both histories were written mostly by agents (Claude) for one owner, with large commits and descriptive messages. Human-written histories with small `fix: …` commits and issue references (the mastra and better-auth forks) could behave differently. H1 in particular deserves a re-run there before the idea is dropped for good.
- **One reader** judged the 50 commits for regex precision, from messages only, with no diffs read. Precision and recall carry roughly ±15 to 25 points.
- **The hand-checked sets are small.** There is one correct retire in all of S6, 6 correct same-shape clusters, and 8 correct and 11 wrong pins. No conclusion rests on comparing judged correct with judged wrong items. The population checks carry the verdicts.
- **Blame sees only last touches.** "Edited later" misses edits that were overwritten, so H3 undercounts co-change. A per-test `git log -L` was not available from the exports.
- **The small-fix threshold (5 tests) was chosen after seeing the bulk commits.** The other definitions were fixed before the H1 results.
- **H4's live times come from a synthetic replay**: linear, synthetic text, on a heavily loaded machine. They were not measured on the real repositories, because git could not run there from this worktree.
- **The squash simulation** uses the merge commit's own message as the squashed message. A real GitHub squash message (PR title plus a list of commit subjects) carries more words.
- **Not tried:** fault-tag (`[fault:`) workflows (1 match in Assay, 3 in CodeCrystal), issue-tracker links, PR metadata, and test titles as a regression signal.
