# S16 — Flow, orchestration and verified reuse

Date: 2026-10-25. Status: completed; product changes verified and installed privately.

The owner reopened performance work after S12b, asking why validation/tracing
cost more, whether Rust could help, and explicitly requesting a rethink of the
flow, orchestration, caching and reuse. This is a new bounded pass. S12b's
recorded failure and the accepted private handoff remain historical evidence.
No public release, network feature or native rewrite is authorized by this pass.

## Observed problem

The existing one-file Express selected call has median stages around 80 ms
decision, 40 ms policy, 166 ms capture and 43 ms assessment: 327 ms total versus
131 ms privacy-guarded full. Its actual Node process takes about 75 ms; capture
contains another approximately 91 ms of host work. Two-file selection costs
414 ms versus 133 ms full, with approximately 155 ms of sequential child work.
The recorded inventory is 964 files / 8,559,996 bytes, excluding opaque `.npmrc`.

The source currently scans HEAD five times across its separate APIs, repeats
lock/package/dependency/source identity work, and launches selected files
sequentially. These are orchestration costs, not a measurement that the pure JS
engine needs replacing. SHA-256 uses Node's native crypto interface already.
V8 coverage, target test execution and process startup remain with a Rust port.

## Slice A: one coherent selected request

Implement only under `plans/spikes/s16/`; retain the S12b source and original
test-process hooks. An internal synchronous coordinator accepts bundle, trusted
baseline arguments, base/head roots, full test inventory, explicit input policy,
Node executable, private output directory and a required expected producer hash.
It returns decision, capture, assessment, phase timings and operation counters.

Execution order:

1. Validate baseline identity and evidence once against current bytes.
2. Build one HEAD pre snapshot after complete metadata/privacy preflight. Bind
   bytes, lock, installed metadata, observed dependencies, runtime and policy.
3. Reuse that private snapshot for selection, policy and capture setup. No
   caller-provided snapshot, `validated: true`, reusable context or callback.
4. Run the same fresh, isolated, guarded process per selected file. Scheduling,
   tracing, required repeats and supported API boundaries do not change here.
5. Build one fresh HEAD post snapshot; check repository, lock, dependencies,
   opaque descriptor, completion and every denial against actual post-run data.
6. Assess the trace using those post-run verified facts and return a scoped
   result. A subset never becomes a whole-suite guard pass.

Expected inventory passes: baseline **1**, HEAD **2**, versus baseline **1**,
HEAD **5** before. Cross-request/mtime caches and narrowed inventories are not
part of this slice. Immutable within-phase facts may be reused; mandatory fresh
post-run verification remains.

Producer identity explicitly separates original reference profile hash
`67cb560222d1667eb7628e9b09db586f814167c815e2c21a61e66e5528de230b`, actually executed
hook-source hash, and coordinator/transitive host helper/engine/schema hashes.
Their composite hash is compared with the required independent expected pin
inside the measured API before and after execution. The new launcher never
claims to be the old producer. Freeze only after all source dependencies stop
changing.

## Slice B: pure engine work proportional to the requested view

Preserve complete reports, diagnostics, ordering, exits and pure Workers
portability. Product changes are restricted initially to:

- Skip advice for guard/validate when its outputs and diagnostics do not use it.
- Compare consolidation candidates within file/criticality buckets, preserving
  union roots and final canonical group ordering.
- Reuse a duplicate lookup within the same advice call and group file-summary
  rows once where source proof permits it. Do not retain quadratic partner lists.

Before editing, save the original engine and oracle reports in ignored scratch.
Compare all conformance cases, deterministic generated cases, and the actual
65-row input. Synthetic scale cases are labeled synthetic. Existing mutation's
lightweight model and schema cache remain; do not replace them with a heavy
general model or claim they were absent.

## Correctness and measurements

- Run actual coordinator controls on Node 22.23.3 and 26.7.0: exact old/new
  selections and result rows, wrong/missing producer pin, spoofed contexts,
  policy/cross-root/stale input, lock/install identity, source/dependency mutation
  during execution, symlink/opaque descriptor, missing/truncated/caught-denial
  proof. No `.npmrc` content reads or hashes.
- Replay all original 15 scenarios on both runtimes with strict and approved
  opaque policy. Keep the source-text counterexample and exact expected refusals.
- Preserve the complete pinned Express lane (65 IDs), both real source faults,
  ordinary privacy-guarded full proof and selected-head proof.
- Run five alternating paired samples for old/candidate and candidate/full.
  No simultaneous CPU-heavy tests or other benchmark workers. Count every
  mandatory pin, validation, execution and post-run check in whole-call wall.
- Run diagnostic instrumentation separately from uninstrumented timings.
  Count inventory/read bytes, metadata calls, lock/package/observed-dependency
  work, trusted source hashes, process time and trace volume. Record CPU and
  RSS separately. Fresh-process is not a claim of a cold OS filesystem cache.
- Engine changes require whole report+exit equivalence. Measure pure-engine
  latency and full CLI startup separately, using actual input and labeled
  synthetic scale. Any product adoption requires full verify and Node 22 tests.

Call Slice A a useful optimization only if both real cases improve old selected
median by at least 20% and win four of five pairs, with all safety results equal.
Production selective usefulness still requires four of five wins versus full
and at least 10 ms median saving in both cases. Report the two decisions
separately. No automatic chain into parallelism or Rust follows a failed slice.

### Pure engine flow

All 120 frozen complete reports and exits matched after skipping unused advice
for guard/validate, bucketing consolidation comparisons, and reusing local
duplicate/file indexes. Focused tests passed on both Node runtimes.

- Actual 65-row full CLI `guard`: median 80.41 → 76.12 ms; a small 4.29 ms gain.
- Actual 65-row engine-only `report`: 7.06 → 7.17 ms; no measured improvement.
- Labeled synthetic 10,000-unit engine report: 777.93 → 535.96 ms, **31.1% faster**.
- Separate synthetic after-run RSS readings were slightly higher; this is not a

### Explicit MCP report reuse

The product now supports `cupel_report` with `retain: true`; later calls name
the returned `snapshotId` plus page/pageSize. The server retains the complete
immutable report, bounded to 8 entries / 32 MiB with root binding and checksum
checks. Replays run **zero CLI, collector and mutation calls** in the focused
tests and are explicitly historical. Ordinary calls remain fresh. Missing,
evicted, corrupt or oversized snapshots produce errors, never a hidden rerun.
Guard cannot accept a report snapshot.

Seventeen focused MCP tests passed on both exact Node runtimes, including
pagination parity, caller mutation, size/LRU bounds, corruption accounting,
process/root separation and stdio replay. These are report-output snapshots;
general input/model snapshots and persistent static-analysis caches remain
planned rather than implemented. Installed artifact acceptance is a separate
handoff gate. See [`docs/mcp.md`](../../docs/mcp.md).

Rust was not introduced. The measured changes remove work and improve flow while
retaining the deterministic, portable engine and existing runtime isolation.
