# S6: Is draft advice credible to a person?

## Question

Build a draft engine that turns measured signals (unique coverage, unique mutation kills, redundancy, cost, brittleness, tier) into keep, consolidate, rewrite and retire advice with reasons. Run it on Vibernt Assay's Node suite and CodeCrystal's pytest suite. Hand-check 30 suggestions per suite by reading each test and the code it exercises, and judge each one correct, wrong or debatable. Report the precision of retire and consolidate advice per suite, and explain every false positive.

## Answer in brief

**No, not with the draft rules. Retire and consolidate advice built on line coverage is not credible.** One round of rule changes made consolidate and rewrite advice credible on narrow grounds. Retire advice should not ship on coverage evidence alone.

| Advice | Assay v0 | CodeCrystal v0 | Assay v1 (tuned, fresh sample) | CodeCrystal v1 (tuned, fresh sample) |
|---|---|---|---|---|
| retire | **0 / 10** correct (0 % strict, 0 % lenient) | **1 / 10** (10 %, 20 %) | none advised | none advised |
| consolidate | **0 / 10** (0 %, 0 %) | **0 / 10** (0 %, 10 %) | 2 / 10 (20 %, 50 %) | **7 / 10** (70 %, 100 %) |
| rewrite | 3 / 10 (30 %, 40 %) | 3 / 10 (30 %, 80 %) | 5 / 10 (50 %, 50 %) | 3 / 3 (100 %, 100 %) |

Strict precision counts only "correct"; lenient also counts "debatable". The v1 consolidate figures mix two rules:

- **Same-shape siblings** (new in v1): 8 of 11 correct and 3 debatable across both suites (73 % strict, 100 % lenient).
- **File groups** (unchanged from v0): 1 of 9 correct and 3 debatable (11 % strict, 44 % lenient).

What went wrong in v0:

- **Retire.** 19 of 20 retire suggestions named a test that a person would keep, or one whose value is debatable. The one correct suggestion repeats half of a test in another file. The others had no unique *lines*, but they had unique *assertions*. Other tests ran its code without checking what it checks: integration tests, fixture sweeps and end-to-end flows over a unit-tested function. Other causes were rows of a parametrized table, security tests the tier rule missed, and tests of config or docs that cover no code.
- **Consolidate.** "Lines are a subset of a same-file sibling" is the normal state of a well-organised unit-test file. It fired on 709 Assay tests and 684 CodeCrystal tests. The siblings asserted different behaviours, or were rows of a table that already exists.
- **Rewrite.** The brittleness detector was right about source-text pins and wrong about fixtures, parsed config and taint that leaked between scopes.

What worked after tuning:

- **Consolidate** when two tests in one file have nearly the same body with different literals (token-shape similarity at least 0.8 and own-line Jaccard at least 0.3).
- **Rewrite** for real source-text and CSS pins, flagged by a stricter detector.
- **Retire** only when it is corroborated, and nothing qualified. 1,059 Assay units and 397 CodeCrystal units were retire candidates on coverage alone. v1 keeps them and marks them "unverified".

The per-process re-check of retire candidates (D7) turned 1 of 744 Assay candidates and 3 of 107 CodeCrystal candidates into keep.

**The pytest collector** uses `sys.monitoring`, PY_START and LINE, with per-test restarts. It records every test in one ordinary run. Its own bookkeeping is small: 3,171 restarts cost 0.08 s and the JSON write 0.19 s.

The spike found and fixed one collector bug: code objects compare equal by value, so a module loaded twice under two names went unrecorded the second time. Its overhead is in the "pytest collector overhead" section below.

## Method

### Signals

**Assay per-test coverage** came from S2's method B: one ordinary `node --test tests/*.test.mjs` run with an `--import` preload that takes V8 precise coverage at test boundaries.

- The preload is `s6/node-hook.mjs`, a copy of `s2/hook.mjs` with one change. **The scope is the whole repository minus `tests/`, `node_modules` and dot-directories**, as S1 and D7 recommend, not `src/` and `public/`.
- The run took 53.5 s wall and 478 CPU-s, against 36.7 s and 332 CPU-s plain: 1.46× wall and 1.44× CPU, contended. That matches S2.
- `s6/collect-node.mjs reduce` turns the output into per-leaf-test line sets.
- Setup lines are subtracted from every test, as in S2: module load, root hooks, and between-test and teardown segments of any file.
- Per-file numbers come from the same data.

**CodeCrystal per-test coverage** came from `s6/cupel_s6_pytest.py`, a standard-library pytest plugin loaded with `-p`. It is the seed of `packages/cupel-py`.

- It claims one `sys.monitoring` tool id. The only global event is PY_START.
- The first PY_START of a code object in scope switches on LINE events for that code object alone (`set_local_events`). Code out of scope returns DISABLE.
- The LINE callback records `(file, line)` in the current bucket and returns DISABLE.
- At each bucket switch, `restart_events()` re-arms everything, so each test records its own first execution of each line.
- Buckets:
  - "setup" until the first test, which covers plugin load, conftest and collection imports.
  - One bucket per test, from `pytest_runtest_setup` to the end of its teardown report. Fixtures, call and teardown all belong to the test.
  - "between" after each test.
  - "teardown" after the session.
- Subprocess launches are counted per test by wrapping `subprocess.Popen.__init__`.
- The scope is the copy's whole tree minus `tests/`, dot-directories and virtualenvs. The brief said `src/` only; the deviation and its effect are explained under "Scope matters" below.

**Unique coverage** of a test is the lines in its own set (setup removed) that no other test covers.

**Unique kills** (Assay only) are the mutants that exactly one named test killed, provided no file killed the mutant without naming a failing test (a timeout). A test's evidence is "mutation+coverage" when its own lines touch a mutated file, and "coverage-only" otherwise.

**The D7 re-check.** Every retire candidate was re-run alone and its unique lines recomputed against everyone else's.

- Assay: S2's method A, `node --test-name-pattern` with `NODE_V8_COVERAGE`, in `s6/recheck-node.mjs`.
- CodeCrystal: `pytest <nodeid>` with the plugin, in `s6/recheck-pytest.mjs`.
- A test that shows a line nobody else covers becomes keep.

**Brittleness** is a static detector per test: `s6/detect-js.mjs` (S3's lexer) and `s6/detect_py.py` (`ast`). It reports four patterns:

| Pattern | Rule (default, v0) |
|---|---|
| source-text | The test reads a code file (by extension or by a path under `src/`, `public/`, `scripts/` and similar) as text, directly, through a module-level name, or through a helper that reads, and has a text assertion (`match`, `includes`, `in`, `==`, `re.search` and similar) |
| doc-wording | The same for `.md`, `.txt`, `docs/`, README, CHANGELOG |
| css-class | A `.css` file read and asserted on, or a string or regex in the test containing `class=`, `className`, `classList`, or a CSS rule |
| file-snapshot | An equality assertion that holds a whole-file read, or a snapshot API |

The Python detector counts a read only when its path is anchored on `__file__` or a module-level root constant, so files a test wrote into `tmp_path` never count. Reads that only feed `fixtures/` inputs and JSON reads are never flags.

**Tier.** D4's critical words (auth, permissions, tenancy, tokens, secrets, egress, billing, quotas, migrations, backups, deletion, public API as `contracts/` and `openapi`) are matched against the test file's name and against the paths of the source files the test covers (its own lines). A test is critical on either match.

- Assay: 1,879 tests are critical, 1,578 of them only because they cover a critical source. Most API tests pass through permissions.
- CodeCrystal: 35 tests are critical.
- Minor: doc-file test names, or tests whose only flags are doc-wording or css-class.

### Draft rules (v0, `s6/config.json`)

The first rule that applies wins:

1. Brittle (any kind) → **rewrite** (replace the pins with behaviour assertions).
2. Critical → **keep**.
3. At least 1 unique line or at least 1 unique kill → **keep**. Slow (2,000 ms or more) with fewer than 5 unique lines and no unique kill → **rewrite** (move down a layer).
4. Spawns an interpreter (node or python), so part of its coverage is invisible → **keep**.
5. No own line beyond setup → **retire**.
6. Own lines are a subset of a same-file sibling's, or own-line Jaccard with a sibling is at least 0.9 → **consolidate**.
7. Otherwise → **retire**.

A retire candidate whose per-process re-check shows a unique line becomes keep.

**File groups.** Test files whose primary target is the same source file (the most file-specific lines covered), and whose names are token prefixes of one another, are advised to **consolidate into one file**. Examples: `fanout` and `fanout-cost`, `test_intent` and `test_intent_change`.

### Sampling and judging

`s6/sample.mjs` draws 10 retire, 10 consolidate (tests and file groups together) and 10 rewrite suggestions per suite. It uses a seeded Fisher-Yates shuffle (mulberry32): seed 6 for v0, and seed 7 for v1 with every v0 item excluded, so the v1 sample is fresh.

For each item I read the test, its siblings, the source it covers (via `s6/show.mjs`, which also lists the other tests covering the same lines), and the assertions of the strongest overlapping tests. I then asked: **would a maintainer accept this change?**

- **correct**: yes, as stated.
- **wrong**: no; it would lose a check, merge unrelated things, or rewrite something that is not a pin.
- **debatable**: reasonable people would differ. Examples: a deliberate freshness gate on a generated doc, or a docs link checker.

A consolidate suggestion counts as correct only when the target sibling it names is right.

### One round of tuning (v1, `s6/config-tuned.json` and `--strict` detectors)

Each change answers a false-positive cause found in v0 (see "False positives"):

1. **Group rows.** Rows of one parametrized or looped test (same source location) are judged as one unit. This gives Assay 29 multi-row units and CodeCrystal 95.
2. **Widen the critical tier.** Test file names also match credential, crypto, leak, unsafe, sign-in, login, security, isolation, sandbox, privacy, integrity, redact, phish, inject, travers, hardening, admission and budget. Test titles that mention negative, security, forged, tamper, leak, credential, secret, token, permission, unsafe, traversal, injection, phish or refuse(s) are critical too.
3. **Not run is no evidence.** Skipped or failed tests get no advice.
4. **No coverage is no evidence.** A test with no own lines (config, docs or constant checks) is kept and marked unverified, instead of retired.
5. **Retire only when corroborated.** Either a near-duplicate body (shape similarity at least 0.9 with a test whose own lines contain this one's), or mutation evidence (in a mutated area, no unique kill, at least one kill). Otherwise keep, marked `unverifiedRetire`.
6. **Consolidate only same-shape siblings.** Two tests in one file whose masked bodies (strings, numbers and regexes replaced, 4-token shingles) have Jaccard similarity at least 0.8 and own-line Jaccard at least 0.3. This replaces "subset of a sibling". It applies whatever the unique coverage, because merging keeps coverage. A critical test only consolidates into a critical sibling.
7. **Stricter detectors** (`--strict`):
   - only module-level reads and declarations taint a name;
   - a path naming a fixture is input unless it names an expected, golden or snapshot file;
   - file-snapshot needs the read as a direct argument of the equality assertion;
   - source-text and doc-wording need an assertion with a literal regex or string;
   - css strings count only inside assertions;
   - in Python, reads wrapped in parsers (`json.loads`, `tomllib.loads` and similar) are data, and helpers count as readers only when they return the read directly (hashes are not text).

The shape thresholds were first set at 0.85 and 0.6. That gave almost no suggestions on Assay. After one look at the distribution of best same-file shape similarity and its top pairs (`s6/shape-stats.mjs`: Assay has only 10 tests at 0.8 or more, CodeCrystal 21), they were lowered once, to 0.8 and 0.3. They were not tuned on the v0 sample, but they were set on these two suites.

### Scope matters (CodeCrystal)

**At `src/`-only scope, v0 advises retiring 546 CodeCrystal tests instead of 104**, and consolidating 518 instead of 684. Tests of `scripts/`, `benchmarks/` and `tools/` cover nothing in `src/` and so look worthless. This is S1's finding again, in Python: Cupel's pytest collector must count the whole repository by default. That is why the plugin records repository scope, against the brief's "only `src/`". Recording `src/` alone would not have been cheaper in any way that mattered: the bookkeeping already costs 0.2 s per suite.

### The D7 re-check, and a collector bug it exposed

The first CodeCrystal collection had a plugin bug. The plugin kept armed code objects in a `set`, and code objects compare equal by value. `tests/test_file_read_screen_tools.py` loads `src/cri/filetools` a second time under another module name, a deliberate frozen facade, `_file_r1_frozen_filetools`. After that, the original package's code objects counted as already armed, and about 27 filetools tests that ran later recorded no filetools lines.

The per-process re-check caught it: 24 of 132 retire candidates showed their own lines when run alone. The plugin now keys armed code objects by `id()` and keeps them alive.

All CodeCrystal numbers and samples in this report come from a second collection with the fixed plugin (`coverage-r3`). The first run's samples are kept as extra evidence (rounds `v0-firstrun` and `v1-firstrun` in `results/judgements.json`). They gave a similar result: v0 retire 0 of 10 correct and 2 debatable; v0 consolidate 0 of 10 and 1 debatable.

With the fix, the re-check turns 3 of 107 CodeCrystal candidates into keep (the cause of these 3 was not examined). On Assay (Node) it turns 1 of 744: node:test's process per file already isolates files.

**Lesson for the collector:** identity, not equality, for code objects. A re-check per process stays worth its cost: Assay took 62 s for 744 tests, CodeCrystal 38 s for 107.

## Recommended rules and thresholds for the spec (M2)

1. **Retire is never advised on coverage alone.** A retire suggestion needs all of:
   - not critical;
   - ran and passed;
   - no unique line after the per-process re-check;
   - **no unique kill from mutants on its own lines** (targeted mutation on the candidate's covered lines, not just critical modules), or a near-duplicate body (masked-shape similarity at least 0.9) in a test that covers all its lines.

   Without that evidence, report "no unique coverage (unverified)". This is a review hint, not advice, and should be worded so that nobody mistakes it for retire. D5 should change accordingly: "no unique coverage **and no unique kill on its own lines**, measured; absence of mutation data is not 'no kill'".
2. **The unit of advice is the test definition, not the test id.** Parametrized and looped rows are one unit; advice about a single row is never given.
3. **No coverage is no evidence.** Tests with no own lines (config, docs, constants) get no keep, retire or consolidate advice from coverage. Only the brittleness detector speaks about them.
4. **Consolidate only same-shape siblings.** Use masked-token shingles (k = 4, strings, numbers and regexes masked): similarity at least 0.8, own-line Jaccard at least 0.3, same file. Advise one consolidation per cluster, not one per pair (the v1 sample counted pairs twice). A critical test consolidates only with critical siblings. Drop "line set is a subset of a sibling's" as a consolidate signal.
5. **File consolidation is off by default.** If kept, only for small files (10 tests or fewer and 300 lines or fewer each) that share a primary target and a name prefix.
6. **Critical tier.** Use D4's words, plus credential, crypto, leak, unsafe, sign-in, login, security, isolation, sandbox, privacy, integrity, redact, inject, traversal, phish, hardening, admission and budget, on test file names and covered source paths. Also tag titles containing "negative", "security", "forged", "tamper", "refuse(s)", "permission", "token", "secret", "credential" or "unsafe". "Covers a critical source" (any line) makes 40 % of Assay's tests critical (1,578 on that rule alone); that is safe for retire (critical is never retired) but too broad for prioritisation. The spec should keep "covers any critical line" for the never-retire guard, and use "unique lines in a critical source" or name and tag matches for the run order.
7. **Rewrite (brittle pins)** with the strict detector rules above, plus the next-round fixes. Report the pin kind and line. Label deliberate pins (generated-file freshness, provenance hashes, sync checks) as "pin (deliberate): move to a check", not "rewrite".
8. **Slow and low value**: 2,000 ms or more and fewer than 5 unique lines, from the median of at least 2 runs.
9. **Counting scope** is the whole repository minus `tests/`, dependency and virtualenv directories, and dot-directories, for Python as for Node. At `src/`-only scope, v0 would have advised 546 CodeCrystal retires instead of 104.
10. **Collector re-checks.** Re-check every retire candidate per process (cheap: Assay 744 tests in 62 s, CodeCrystal 107 in 38 s), and give no advice to tests that spawn an interpreter. The pytest collector must track code objects by identity.

**Verdict: on CodeCrystal the collector's overhead is within the noise of a contended machine, and at most about 7 % of in-process CPU.**

- Whole-suite repeats of the same mode differed by up to 58 %. CodeCrystal's suite spends most of its time in subprocesses (git, python) and waits: user CPU is about 0.4 of wall.
- `sys.monitoring` with per-code-object LINE events and DISABLE records each line at most once per test, so the cost grows with the number of distinct lines a test runs, not with loop iterations.
- Measured in the plugin itself:
  - 3,171 restarts (two per test) took 0.08 s;
  - building and writing the 3.2 MB JSON took 0.19 s;
  - the session ran for 320 s.
- **Not measured:** a CPU-bound pure-Python suite on an idle machine (the worst case), and Python 3.12 or 3.13.
- For comparison, the Assay node:test collection (S2's method B, whole-repository scope) cost **1.46× wall and 1.44× CPU** against a plain run, contended. That matches S2's figure of about 1.4×.

## Caveats and what was not verified
