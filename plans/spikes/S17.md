# S17: per-request mutation source facts

## Question and method

Can Cupel reuse source text and lexical facts within a mutation request without
reusing test outcomes or weakening source freshness? We froze pre-change
mutation outputs and source modules on Node 22/26, then compared three exact
implementations: legacy, repaired path/freshness guards without reuse, and the
same guards with lexical/batch-text reuse. Inputs and source hashes were pinned.
The workloads were the existing node:test mutation fixture (4 tests), existing
Jest conformance fixture (8 tests), and an explicitly synthetic 703-line
source-heavy project (3 actual collected tests). Complete method, controls,
raw locations and limitations are in [s17/RESULTS.md](s17/RESULTS.md).

## Numbers

- Full mutation and confirmation output, legacy run counters, and fresh runner
  launches matched exactly across all three implementations on Node 22.23.3
  and 26.7.0.
- At `jobs:1`, source reads old/guards/reuse were 8/49/49 for node:test,
  3/15/15 for Jest, and 10/75/75 for the synthetic case. The added reads are
  freshness checks; reuse made no read difference with one mutant per batch.
- In a separate `jobs:2` diagnostic, same-guard mutation reads fell 29→26,
  13→12 and 37→33. Test/Jest launch counts stayed equal. This is read-count
  evidence, not a wall-time speed claim.
- Five alternating whole-request triplets on Node 26 produced median
  legacy/guards/reuse wall: node:test **818.93/820.12/825.04 ms**; Jest
  **2104.13/2113.90/2119.53 ms**; synthetic **1271.84/1271.81/1264.44 ms**.
  Same-guard reuse was faster in 0/5, 2/5 and 4/5 pairs respectively. Parent
  CPU, RSS and retained heap are reported separately in the detailed result.
- Accounted retained source facts were 144, 76 and 20,125 bytes, all below
  the 32 MiB fact-payload cap. This cap is not an RSS limit.

## Verdict

The source-path and per-execution freshness checks provide a safety correction
and should be reviewed on that basis. The reuse change preserves exact outputs
and saves 1–4 reads with two-mutant batches, but this experiment does **not**
show a broad whole-mutation latency benefit. The original candidate hash
`53a8f654…` was revoked after a pre-read path issue and was never timed.
The repaired code refuses unsafe/hard-linked paths, opaque supplied hashes and
hosts without `O_NOFOLLOW`; no fallback is used. SourceFacts hashes source
bytes and binds logical/real paths, device/inode and request-issued facts. It
does not hash parser/runtime/config/schema identities. Test outcomes remain
fresh on every mutation and confirmation run.

## Adoption

Adopted as a source-integrity correction after the required Node 26 verification
and Node 22 test gates passed with **455 Node outcomes each**, plus **38 Python
tests** and **17 Ruby tests / 75 assertions**. Fresh package smokes required
Jest and offline npm/wheel installation. The installed private handoff also
passed Python 5/5, historical MCP report replay, real Jest guard pass and
weakened-assertion failure, and a source-write negative that exited 3 with a
source-changed error. See `plans/RELEASE-READINESS.md` for the current artifact
and raw gate paths. This adoption is not a general speedup claim.

Next best action: finish the full correctness gates and adopt the safety
correction, then profile repeated coverage parsing in `Session.select` before
one bounded cache change. The current data does not support a broad speed
claim. No production release or external-repository acceptance was performed.
