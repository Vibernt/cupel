# S11 — Go per-test coverage cost and runtime boundary probe

Date: 2026-10-24. Platform: darwin/arm64. Go: go1.27.1. Node benchmark runtime: v26.7.0. Available parallelism: 12; existing collector worker limit: 6.
Baseline: `a7c7180a36b254e51aa63c2ad922f4e02f8d57bc`.

## Verdict and scope

Ship the block-to-K1-line cache as the default, with no flag and no changed execution semantics. The controlled comparison reduced collection from **47.41 s to 29.53 s**, a **1.61x speedup / 37.7% wall-time reduction**. The resulting ratio to plain `go test -count=1 ./...` is **5.34x** (another run was **5.08x**). This is near the task's “about 5x” cheap-fix exception, not a demonstrated hard ceiling of 5.00x.

**The in-process runtime/coverage candidate does not work with this installed Go test harness.** The overlay itself works, but every required coverage API fails before test teardown. No internal runtime hooks, unsafe/linkname access, custom harness, or automatic alternative was introduced. The existing process-per-test collector remains in use. This is not a completed in-process implementation or a claim that the 21-minute real-repository case has been solved.

## Method and reproduction

All commands are offline; generated modules, cache, binaries, profiles, baseline copies and raw measurements live under `.scratch/s11/`. No original repository source is rewritten by the collector or probe. Only this designated worktree was edited; changes remain uncommitted.

```sh
node bench/s11/generate.mjs
node bench/s11/measure.mjs
node bench/s11/costs.mjs
node bench/s11/probe.mjs
```

`measure.mjs` reads the pinned baseline with `git show`, copies its collector to scratch, and instruments process elapsed times and synchronous profile/subtraction time. It also copies/instruments the current collector, so the two measurements use the same observation method. It warms plain Go once, measures `go test -count=1 ./...`, collects with `runs: 2`, and compares the entire input after removing only `tests[].durationsMs`. It forces `GOPROXY=off`, `GOSUMDB=off`, `GOTOOLCHAIN=local`, and a shared scratch GOCACHE. There are no new dependencies.

The stdlib-only generated module has:

- 30 production packages; a chain of imports into previous packages.
- 1,000 top-level tests: 880 internal and 120 external-package tests.
- 40 production branch functions per package, plus cross-package wrappers.
- Five initializers doing 200,000 loop iterations each.
- Three top-level parallel tests; 60 parents with subtests.
- One package with its own `TestMain`, with production calls both before and after `m.Run()`.

The generator is deterministic and has a test checking those counts and repeatability. Plain Go runs include all tests once; Cupel measurements use two repeats, plus its existing all-package source discovery/setup passes. This matches the default collector's workload rather than pretending it performs the same amount of work as one plain run.

### Startup, test body and coverprofile emission

`costs.mjs` builds three representative package binaries and alternates 15 empty runs without a profile, empty runs with a profile, single-test runs, and 1,000 repeats of one test. Binaries use the original `count` mode and whole-module `coverpkg`. Median empty-run time measures process start plus package initialization; the paired profile difference estimates profile emission. Repeated-test timing bounds test body **plus testing harness** time; individual synthetic bodies are too short to isolate reliably from subprocess timing. Results (medians of 15 samples per scenario, milliseconds):

| Package | Startup + init | Empty run + profile | Profile writing estimate | Body + harness per repeat |
|---|---:|---:|---:|---:|
| p00 (initializer, no imports) | 5.497 | 5.857 | 0.360 | 0.00971 |
| p05 (TestMain, 6-package graph) | 5.509 | 7.861 | 2.352 | 0.00979 |
| p29 (30-package graph) | 10.469 | 22.228 | 11.760 | 0.00944 |

The whole-module coverpkg argument is identical for each binary, but Go only includes the reachable package graph: profiles contain 202 / 1,207 / 6,039 block rows and occupy 9,587 / 57,232 / 286,308 bytes respectively. The first launch of a newly built binary is excluded from these paired microbenchmarks; the full collector listing phase above includes it.

Replaying the exact same p29 profile 2,000 times, with setup subtraction and a warm source cache, took **58.869 s before / 5.007 s after (11.76x)**. That isolates parser/subtraction work from processes and compilation. It is not an end-to-end speedup claim. Exact pure-body CPU time is not measured; the roughly 9.4–9.8 microseconds per repeat includes the Go testing harness. Process startup/init and profile emission dominate those tiny bodies.

## The shipped change

`coverage.mjs` now caches each block's source path, byte-column-to-character conversion, K1 line set and block key once per collection. The cache key excludes the execution count, which is always read anew. Cache ownership remains the existing collection-local Map; there is no cross-root or cross-invocation state. Zero-count blocks still contribute coverable lines; counts still drive subtraction, so a test executing an initialization block again is attributed correctly. Every row still receives the existing syntax validation and package/path filtering.

No parallelism, process isolation, setup subtraction, K13 repeat behavior or output fields changed. The parser's measured time fell by 89.3%; subtraction was already small. No zero-row shortcut was introduced that would erase uncovered source lines.

## Step 2: runtime/coverage and overlay findings

The reproducible probe builds an atomic covered test binary with `go test -c -overlay`. It substitutes a copied `_test.go` file with a first-statement boundary on the same physical line and adds a virtual helper test file. The original test file is checked for byte equality afterward. Both `GOCOVERDIR` and `-test.gocoverdir` are supplied.

Observed inside the test on Go 1.27.1:

```text
WriteMetaDir: error: no meta-data available (binary not built with -cover?)
WriteMeta: error: no meta-data available (binary not built with -cover?)
WriteCountersDir: WriteCountersDir invoked for program built with -covermode=<invalid> (please use -covermode=atomic)
WriteCounters: WriteCounters invoked for program built with -covermode=<invalid> (please use -covermode=atomic)
ClearCounters: ClearCounters invoked for program built with -covermode=<invalid> (please use -covermode=atomic)
```

The local toolchain source explains the behavior:

- `src/runtime/coverage/coverage.go`: ClearCounters requires atomic mode.
- `src/internal/coverage/cfile/apis.go`: metadata needs `finalHashComputed`; counter writes and clearing require the initialized atomic mode.
- `src/internal/coverage/cfile/hooks.go`: `InitHook(istest=true)` registers metadata emission for exit, whereas non-test executables initialize it immediately.
- `src/internal/coverage/cfile/testsupport.go` and `src/testing/newcover.go`: ordinary test coverage finalization occurs at test teardown.

Thus selecting atomic instrumentation is necessary but **not sufficient** for these APIs inside the ordinary test harness. `go tool covdata` is also absent from this installation (`go: no such tool "covdata"`), though its source is installed. No tool was downloaded or implicitly rebuilt. Even with a working covdata tool, merging all directories into a single textfmt output would lose per-test identity; a future implementation needs an identity-preserving conversion strategy.

Additional correctness requirements for any redesigned harness:

- Register the end snapshot as the first `t.Cleanup`, so it runs after later cleanups and parallel child subtests. A plain deferred function ends too early.
- Internal and external test packages need separate helpers, coordinated against the same runtime counters.
- Detect top-level parallel behavior, including calls hidden in helpers, before permitting overlapping snapshots. A direct lexical `t.Parallel()` check is not a complete general detector.
- Process isolation changes mutable package-global state and `sync.Once` behavior. Passing a synthetic parity test would not prove parity for stateful suites.
- Preserve the existing TestMain coverage window explicitly. In this toolchain, the production call before `m.Run()` appears in setup; the call after `m.Run()` is absent because the harness already emitted its profile. Capturing all process-exit work would therefore also change current output. TestMain-controlled state and cleanup need dedicated parity cases.
- K13 repeats must remain separate processes.

### Fallbacks and triggers

**None added.** Parallel tests, TestMain, ordinary tests, failures and crashes still take the original process-per-test path. There is no runtime-API failure that silently selects another implementation.

The task authorized isolated recovery for parallel tests and remaining tests after a crash in an in-process run, but that path was not built because the required public counter APIs fail first. The original Go collector can still error when a panic or `os.Exit` leaves no top-level result; this spike does not claim crash recovery. A separate custom-harness/instrumentation design needs the owner's decision before implementation.

The generated module's **entire input** matches the pinned baseline after removing durations, not merely the requested `tests`, `coverage.byTest`, `coverage.setup` and `sources`. This also checks runtime, tags, shapes, brittleness, rechecked IDs and `unstable`. Scratch `parity.json` records 1,000 tests and success. Runs were two separate processes per test, unchanged.

Focused cache tests cover varying counts on the same coordinates, zero blocks, UTF-8 columns, setup count subtraction, fresh-cache equality, actual reuse of block line sets, malformed rows and unknown packages. The existing Go fixture tests cover hand-written `expected.json`, schema/report validation, K13 instability across three runs, CLI dispatch, test-file filtering and subtest reporting. The synthetic parity comparison additionally exercises internal/external test packages, TestMain and top-level parallel tests through the unchanged execution path.

There is **no production overlay, parallel-boundary recovery or crash-recovery implementation**, so there are no passing tests claimed for those unimplemented features. The overlay/API probe is an executed diagnostic, not a conformance claim for in-process attribution. `npm run verify` passed (Node suite, repository checks, 38 Python tests, 13 Ruby tests / 63 assertions). `PATH=/opt/homebrew/opt/node@22/bin:$PATH npm test` also passed on Node **22.23.3**. `git diff --check` passed. Benchmark, cost replay and overlay probe commands completed successfully; the probe reports the API errors above as diagnostic evidence.

## Rust design note (not implemented)

The analogous experiment would instrument every top-level `#[test]` with a guard that resets LLVM counters at entry, sets a unique per-test output filename, and writes the raw profile when the guard drops. The relevant runtime entry points are `__llvm_profile_reset_counters`, `__llvm_profile_set_filename` and `__llvm_profile_write_file`; their availability and linking must be checked against the installed Rust/LLVM versions before implementation.

Rust has no direct equivalent of Go's source overlay for this workflow. Use an explicitly constructed scratch copy of the workspace, rewrite test sources there, and remap paths back to original source identity. A rustc wrapper that rewrites compiler inputs would need a deliberate design for module resolution, macro-generated tests, build scripts, include paths and dependencies; it is not a transparent substitute. Avoid modifying the user's original files or injecting helpers through network-installed proc macros.

`--test-threads=1` prevents simultaneous top-level harness tests, but is not sufficient for correct attribution: tests can leave worker threads running, process-global state persists, and abort/exit bypass Drop. Tests that spawn child processes require their own profile identities. Keep per-run processes for K13, detect missing end records, and decide explicitly whether isolated retries are authorized. This is a conceptual note, not a validated Rust runtime integration.
