# S1: How much of a real suite adds no unique coverage?

## Question

Run each Node test file of Vibernt Assay alone with `NODE_V8_COVERAGE`, build a line set per file, and count the lines covered by exactly one file. Which files have no unique line, and what does collecting this cost?

## Answer in brief

- 47 of 421 test files (11%) have no unique line in `src/**` and `public/**`, the scope Assay's own `test:coverage` uses. They hold 356 of 4,724 tests and 13.6% of the suite's CPU time. All 47 can be removed together without losing a covered line.
- Half of those 47 only look redundant because of that scope. Counted over the whole repository (everything except `tests/**`, `node_modules` and dot-directories), 24 files (150 tests, 3.5% of CPU) have no unique line. 11 of the 12 files that "cover nothing" in `src/public` test `actions/`, `scripts/`, `sdk/` or `cli/` code.
- Import inflation is large for covered lines but almost nil for unique lines. 20% of all covered lines, and a median of 86% of each file's covered lines, run just because a module was imported. Only 194 of 38,365 unique lines are load-only. Five files cover nothing but load-only lines; they assert on source text.
- Per-file coverage is cheap and stable. Running each file alone, 5 at a time, took 82 s wall and 361 CPU-s; without coverage the same run took 85 s and 349 CPU-s. Two runs produced the same zero-unique list. A single ordinary `node --test` run, with a preload that tags each process with its test file, gives the same per-file line sets and the same 47 files.

## Method

Scripts are in `plans/spikes/s1/`. They are Node ESM, standard library only, and each has a usage comment.

1. `collect.mjs` runs every test file alone: `/usr/bin/time -p node --test --test-reporter=tap <file>` in the suite root, with `NODE_V8_COVERAGE=<out>/cov/<name>`, 5 at a time, in alphabetical order. V8 coverage follows the node child processes a test spawns, because they inherit the environment; their data is kept (648 coverage files for 421 runs). It records wall time, user and sys CPU (from `time`, which includes waited-for children) and the TAP counts. With `--no-coverage`, the same run measures overhead.
2. `reduce.mjs` turns each run's coverage files into `{ path: [lines] }`, using the line rule below. The scope is `src-public` (the default, like Assay's `test:coverage`) or `repo`.
3. `loadonly.mjs` measures import inflation. For each of the 1,032 modules in `src/**` and `public/**`, a fresh process imports only that module and exits. Before the import it loads the suite's `cloudflare:workers` stand-ins (`tests/support/cloudflare-modules.mjs`), and for `public/**` modules it also installs the suite's DOM double (`tests/support/dom.mjs`). Every line covered in any of these runs is a **load-only line**. 10 modules throw on a lone import: 7 in `src/migrate/*` hit an import-cycle temporal dead zone (TDZ) error, and 3 browser entry points in `public/` need a page. Their top-level lines are still captured when other modules import them.
4. `analyze.mjs` computes the tables below, `files.csv`, `zero-unique.csv` and `summary.json`. Line keys are `path:line`. A file's unique lines are those no other test file covers. "Subset of" means the file's line set is contained in a single other file's set; the smallest such file is named. The greedy cover repeatedly picks the file with the most still-uncovered lines.
5. `compare.mjs` diffs two sets of per-run line sets. It was used for a full second collection run (the determinism check) and for the single-run check.
6. `single-run.mjs` is a design check. It runs the whole suite once with plain `node --test`, with `NODE_OPTIONS=--import <preload>`. The preload writes `{pid, ppid, argv}` next to that process's coverage file. A coverage file belongs to the test file named in its own argv, or in its nearest tagged ancestor's argv.

### The line rule (for the spec)

1. **Classify characters.** Every UTF-16 code unit of a source file is whitespace, comment or code. A small lexer handles `//` and `/* */` comments, `'…'` and `"…"` strings, `` `…${…}` `` templates, and regex literals. A `/` starts a regex when the previous significant token cannot end an expression: start of file, one of ``( , = : [ ! & | ? { } ; + - * % < > ~ ^``, or one of the keywords `return typeof instanceof in of new delete void throw case do else yield await`.
2. **Coverable lines.** A line is coverable when it holds at least one code character. Blank lines and comment-only lines are ignored.
3. **Character counts.** For one V8 script entry, every range of every function is painted onto a per-character count array, widest range first. A character's count is therefore the count of the innermost (narrowest) range that contains it. A character inside no range counts 0.
4. **Covered lines.** A coverable line is covered when any code character on it has a count above 0.
5. **Merging entries.** Entries for the same file are merged by taking the union of their covered lines. This covers several processes, child processes, and the same module loaded under two URLs. Only `file://` URLs count, with `?query` and `#hash` stripped.

Consequences to know:
- A function declaration's header line counts as covered at load, because `export`, `async` and the name sit in the module's top-level range.
- A closing-brace line after a `return` is usually uncovered.
- Punctuation-only lines (only `{}()[];,`) make up 13% of coverable lines and 14% of unique lines. No file's unique lines are all punctuation, so excluding them would change no verdict here.

### Stability

A second full collection run differed from the first in 9 of 421 files: 193 lines only in the first run, 14 only in the second. One file, `ui-pipelines-v2`, accounts for 179 of those lines, so the differences come from timing-dependent paths. Unique lines changed by 2 (38,365 to 38,363), and the zero-unique list was identical at both scopes. The single tagged run differed from the first collection in 10 files (310 lines), again with the same 47 zero-unique files. 165 of its coverage files could not be attributed to a test file: the runner itself, and processes started through a shell, which breaks the pid chain. Only 9 of those 165 contained `src/public` lines.

## Verdict

About 1 in 9 Assay test files (47 of 421) adds no unique line coverage under Assay's own coverage scope, and about 1 in 18 (24 of 421) does so at whole-repository scope. Together they hold 7.5% and 3.2% of the tests. They can be removed jointly without losing a line, saving 13.6% and 3.5% of CPU respectively. The answer depends heavily on the counting scope.

This is a ceiling for "retire" advice, not a list to delete. Zero unique coverage says nothing about what the assertions check (S3 measures that). Several of these files are deliberate pins: on generated docs, packaging, or source text. Per-file collection is cheap, deterministic enough for a stable verdict, and needs no runner changes.

## Implications for Cupel

### Collector design

1. **Count the whole repository by default, not the project's coverage include list.** Use every JS file outside `tests/`, `node_modules` and dot-directories, with config to narrow it. Assay's `src/public` scope doubles the zero-unique count, wrongly flagging tests of `actions/`, `scripts/`, `sdk/` and `cli/`.
2. **Use plain `NODE_V8_COVERAGE` and Cupel's own reducer**, not `--experimental-test-coverage`, which aggregates the whole run. The collector should be one ordinary `node --test` run with a pid-tagging `--import` preload. This was verified here: it gives the same per-file sets as 421 isolated runs, uses node's own concurrency, and needs no per-file orchestration. Cupel must tolerate unattributable processes (spawned through a shell) and report how many there were.
3. **Reduce coverage immediately and drop the raw files.** Raw V8 output is about 1 MB per process (625 MB here); the line sets are about 4% of that and could shrink further as ranges or bitsets. Filter out `node:` and non-`file:` scripts before parsing more than needed.
4. **Report load-only lines separately, and use them for a "thin test" signal, not for uniqueness.** They are 20% of covered lines and a median 86% of a file's covered lines, so "lines covered" per test is meaningless without them. They hardly change unique counts, though, because load-only lines are almost always shared. "Covers only load-only lines" (5 files) and "covers fewer than N non-load lines" (39 files under 100) flag tests that pin source text or constants. Measuring load-only lines costs one import per module (27 s for 1,032 modules here). The stub must tolerate modules that throw when imported alone (import cycles, browser entry points) and must reuse the suite's environment shims, which a config hook can supply.
5. **"Covers nothing" is not evidence of a source-text test on its own.** At whole-repo scope it shrinks to 3 files. Cupel's static brittleness check (asserts on source text, CSS, docs) remains necessary and complements coverage.
6. **Determinism.** About 2% of files differ by a few lines between runs, through timing-dependent paths. The spec should either merge N runs (union) or mark lines seen in only some runs as unstable, so a report is reproducible from the same recorded inputs. The engine itself stays pure; the instability lives in the collector.
7. **Line rule.** Adopt the rule above. Leave out punctuation-only lines from the "unique" count; that is optional and changed no verdict here, so the spec could drop them for readability. Branch coverage was not examined.

### D7 (per-file vs per-test coverage in v1)

**Recommendation: ship per-file coverage in v1 as the always-on collector for node:test.** Shape the data model and spec for per-test: coverage keyed by test id, with a `granularity: "file" | "test"` field. Add per-test as an opt-in mode only if S2 shows it costs no more than about 2× a normal run.

Reasons:
- Per-file is essentially free: no measurable overhead beyond a normal run, in a single run. It already finds whole-file retire and consolidate candidates (47 or 24 files here) and the subset and equal pairs.
- Per-file cannot rank the tests inside a file. 62 files have only 1 to 9 unique lines, and per-file keeps every test in them. Per-test "consolidate within a file" advice needs S2's data.
- The final call on D7 waits for S2's per-test cost numbers.

## Caveats and what was not verified

- **Node 26.7.0, not Node 22** (Assay CI). V8 block coverage could differ slightly in its ranges. Not tried on 22.
- **Timings are contended.** S2 and S3 ran at the same time, with load averages of 7 to 80. The coverage-overhead comparison is within noise. The single-run timing (55 s at 11-way concurrency) is not comparable with the 39 s uncontended baseline. CPU for the load-only stubs was not measured.
- **Coverage follows child processes only when they inherit `NODE_V8_COVERAGE`.** Tests that spawn node with a scrubbed environment, or code run in workerd, a browser or Python, are invisible. The workerd suite (163 tests) and the Python suite were not run.
- **Load-only lines are measured for `src/public` modules only.** At whole-repo scope, load-only lines in `scripts/`, `sdk/` and similar folders count as ordinary lines. Import side effects that depend on the environment, and the 10 modules that throw when imported alone, may make the load-only set slightly too small. That is conservative: fewer lines are discounted.
- **The lexer is heuristic.** Regex detection after `)` or `}`, and edge cases such as HTML-like comments, may misclassify a few characters. It was spot-checked on a few files, not tested exhaustively.
- **Generated files** (`public/generated/`, `src/domain/pins.mjs`, `src/api/legal-pages.mjs`) are counted, as Assay's `test:coverage` counts them.
- **Unique coverage is a line measure.** Branches, assertion strength and mutation kills were not considered here (S3).
- **Snapshot status: not checked with git.** The worktree-isolation guard refused `git -C .scratch/assay-s1 status --short`. Instead, `find` listed no file in the snapshot (outside `.git`) modified after the runs started. Files that tests write to the system temp directory were not checked. The caller should run the git status command.
