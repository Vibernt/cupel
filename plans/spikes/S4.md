# S4: Can one area of a real suite shrink without losing anything?

## Question

On a copy of Vibernt Assay, merge `tests/ui-pipelines.test.mjs`, `tests/ui-pipelines-v2.test.mjs` and `tests/ui-pipelines-volt.test.mjs` into one file, and replace their pins (assertions on source text, CSS class names or wording) with assertions on behaviour. It is done when, comparing before and after:

- the test count and the line count are down;
- the runtime is down;
- line coverage is equal or better;
- an S3-style mutation score is equal or better.

The answer also feeds Cupel's "consolidate" and "rewrite" advice: which steps a tool can take, and which need judgement.

## Answer in brief

- **Mostly yes, and the guardrails were needed to get there.** Three of the four done-criteria are met outright; the runtime one is met for CPU but not for wall time in parallel. 42 tests in 3 files (958 lines) became 23 tests in 1 file (869 lines). CPU time fell by 39%, and wall time fell by 46% when the files run one after another. But when `node --test` runs the three old files in parallel on three cores, the one merged file was not faster: its median wall time was 4% higher, within the noise. So the runtime criterion is met for CPU, not for wall time. No covered line was lost (21,562 before, 21,608 after, union of 3 repeats each). The mutation score on the three chosen modules rose from 30.9% to 31.6% on the same 450 mutants, and no kill was lost. The whole-suite score rose from 32.2% to 32.9%, once 11 kills that rested on a flaky test were settled by re-runs.
- **The first rewrite was not safe.** Checking it against the guardrails found 1 lost kill on the chosen modules, 9 lost kills on six more modules where pins were rewritten, and 2 lost covered lines. Each was fixed by restoring or adding one specific assertion (listed below). Without per-test coverage and mutation runs, the weakening would have gone unnoticed: all tests passed.
- **There were no source-text pins.** No test in the three files reads a source file. The pins were 39 CSS class selectors, 31 fixed-copy assertions and 2 copy-style rules. Unlike S3's source-text pins, these read the rendered DOM, so they do earn kills, and deleting them loses detection.
- **A tool found the consolidation groups; a person had to write the merged tests.** Grouping tests by the route they open and by coverage similarity found 4 groups holding 22 of the 42 tests. Every merge of page tests fell inside one of them, though a person split the larger groups (the 9 tests of the pipeline record became 6). The rewrite itself (behaviour queries, table-driven rows, fixture merges) and the choice of what to restore needed judgement.
- **Verdict:** Cupel can credibly advise "consolidate" and "rewrite" here, as advice with evidence, provided `guard` re-runs per-test coverage and mutation on the result. It should not advise "retire" from coverage alone: 2 unit tests here are covered entirely by page tests, but kill mutants that those page tests miss.

## Method

The scripts are in `plans/spikes/s4/`. They are Node ESM, use the standard library only, and reuse S1, S2 and S3's code rather than copying it. Each has a usage comment.

1. **Coverage** (`cover.mjs`). For each test file:
   - Per test: S2's method B (`s2/hook.mjs`, an in-process inspector session that takes precise coverage at test boundaries). We added one option to the hook, `CUPEL_S2_SCOPE=repo`, so it keeps every script in the repository rather than only `src/` and `public/`. Ranges are turned into lines with S1's line rule (`s1/lines.mjs`, scope `repo`: every JS file except `tests/**`, `node_modules` and dot-directories).
   - Per file, as a cross-check: `node --test <file>` with `NODE_V8_COVERAGE`, same line rule.
   - Three repeats per side. `compare.mjs` takes the union over repeats and both methods. A line is "flaky" when only some repeats cover it.
   - Unique lines are counted as in S2: lines only one test covers, and no file's module load covers.
   - The whole-suite view uses S1's per-file line sets for the other 418 files (`.scratch/out-s1/lines-cov-repo`, same commit).
2. **Mutation** (`mutation.mjs` runs S3's `s3/run.mjs`; `kills.mjs` compares two runs). Mutants are served in memory by S3's load hook. Tests are selected by block coverage. A kill needs a reported failing test. Every selected file runs for every mutant (`--stop-after-files 0`), so per-test kills are complete. Timeouts are re-run once with a longer limit. Two scopes:
   - **Area:** only the three old files, or only the new file.
   - **Whole suite:** every test file in the snapshot at that point.
3. **Modules chosen** (`config.json`). We took the three modules with the most lines that only these three files cover in the whole suite (from S1's per-file data). These are `public/app/pages/pipelines/editor.mjs` (277 such lines), `settings.mjs` (253) and `model.mjs` (170). This config is the guardrail.
   - `config-extra.json` adds the six modules where most pins were rewritten (`settings-model`, `detail`, `list`, `new`, `audit` with `audit-model`, and `record-model` with `templates`). It was not required, but a rewrite that weakens a pin shows up there first.
4. **Pins** (`pins.mjs`). A static scan of each test:
   - `source`: reads a source file;
   - `class`: a selector with a CSS class;
   - `copy`: a fixed prose literal of 4 or more words in an assertion's expected value;
   - `style`: a rule about copy (dash characters, text length).

   We also checked which tests earn kills (S3's insight: a source-text pin earns none when mutants are served in memory).
5. **Similarity** (`similar.mjs`). For every pair of tests: the Jaccard similarity of their covered lines outside module load, whether one's lines or kills are a subset of the other's, the route each opens, and the helpers both call. It then groups the tests.
6. **Rewrite**, by hand, into one file (`s4/ui-pipelines.test.mjs`, installed in the snapshot as `tests/ui-pipelines.test.mjs`). The rules are below.
7. **After:** the same measurements, then the guardrails:
   - the after-union of covered lines contains the before-union;
   - the same mutant ids with the same seed;
   - no kill lost, and the score per module and overall is equal or better.

   Each failure was fixed in the tests and measured again.
8. **Timing** (`timing.mjs`): two sessions of 7 interleaved repeats. The before side ran byte-identical copies of the original files, placed in `tests/` under a non-test name, so both sides ran in the same conditions. Two variants:
   - "together": `node --test` with all the side's files, as the suite runs them, in parallel processes;
   - "serial": one `node --test <file>` per file, summed.
9. **Whole suite** once at the end: `node scripts/test-quiet.mjs`, and Assay's test-count guard.

`report.mjs` collects the numbers into `s4/summary.json`.

## What a tool could do, and what needed judgement

| Step | Signal or method | Automatable? |
|---|---|---|
| Choose the area and the mutation modules | lines only these files cover, from per-file coverage of the whole suite (S1 data) | Yes |
| Find same-setup groups | the same route in `harness.open('<path>')` plus coverage Jaccard ≥ 0.8 (`similar.mjs`): 4 groups, 22 tests, matching every page-test merge | Yes, as a proposal |
| Find same-target unit tests | the same imported module and called helpers | Partly. It proposes module-level groups (all 12 `model.mjs` tests). A person split them by concept (formats, problems, formatters, editing) to keep titles meaningful |
| Find exact duplicates | identical covered lines and identical kills | Yes (there were none) |
| Retire candidates | coverage subset | **No, not alone.** Two unit tests are covered entirely by page tests but hold kills those page tests miss. "List filters" lies inside each of 4 list-page tests, yet 2 of its 20 kills are made by no list-page test. "Audit sort" lies inside the audit page test, yet 2 of its 11 kills are not made there. A third, "plan rows", is a subset on both coverage and kills: a real retire candidate (merged here instead). Kill data must veto |
| Find pins | static scan (`pins.mjs`): class selectors, fixed prose in expected values, copy-style rules, source reads | Yes for class selectors and source reads. Copy is noisy: 11 of the 14 "copy" findings after are fixture data |
| Which pins earn kills | per-test kills from in-memory mutants | Yes, but the earning is per test, not per assertion. Knowing which assertion holds a kill needs a mutant-by-assertion run, or a person reading the failing message (S3's runner keeps the first error line, which pointed straight at the regex for `settings.mjs:391`) |
| Write table-driven tests | rows with the same call shape (`filterPipelines`, `intervalLabel`, `isSha`, `ENV_NAME`, roles, old tab ids) | A rewrite an agent can do. Spotting the rows is mechanical; naming the cases is not |
| Replace a pin with behaviour | pick a role, label, link target or data hook; find the data the text carries; decide whether a rule is design (drop) or behaviour (keep) | **Judgement.** Each needed reading the page module. Six replacements were too loose (three loosened copy too far; three dropped a list that was really behaviour: key-fact names, card headings, severity labels), and only the guardrails caught them |
| Merge fixtures | two `definition()` and `pipeline()` builders with different shapes | Judgement, kept as two named builders |
| Check the result | coverage union (3 repeats), the same mutant set, no kill lost, scores equal or better | Yes: `compare.mjs` and `kills.mjs`. About 1.6 minutes per mutation config for this area, and about 6 minutes for the whole suite (most of it the 419-file coverage pass), under load |
| Fix a failed check | read the lost kill's source line and the old failing message, and restore an assertion | Judgement, but well-guided: the report names the line, the operator and the test that used to kill it |

**For Cupel's advice:**
- **Consolidate:** "tests T1…Tn open the same route with the same answers (coverage Jaccard ≥ 0.8); merge them into one test or a table". Show the routes, the Jaccard and the kill sets, so a reviewer can see that nothing unique is dropped.
- **Rewrite:** "test T asserts on styling classes or fixed copy (list); query by role, label, link target or data hook, and assert the data". Show which tests hold kills, and warn that loosening copy can lose a kill.
- **Always:** follow with `guard` on per-test coverage over repeats, and the same seeded mutant set. Treat lines covered only in some repeats as flaky, not as lost or gained.

## Verdict

**Yes, Cupel can advise this credibly, if the advice is checked by `guard`.**
- The signals found the right groups.
- The static scan found every class pin.
- The guardrails (per-test coverage over repeats, and seeded in-memory mutation with no lost kill) caught every weakening a careful manual rewrite introduced: 10 kills and 2 lines in the first pass.
- The result is smaller and uses 39% less CPU, and it lost no coverage and no kill. It is not faster in wall time when the old files would run in parallel.

What Cupel cannot do is write the rewrite: replacing pins needed reading the page code, and 6 of about 35 replacements turned out too loose (they cost 10 kills until restored). "Rewrite" must therefore stay advice to a person or agent, never an automatic change. And "retire" must never rest on coverage alone.

## Caveats and what was not verified

- **One area of one suite.** These are console page tests under a DOM double; server tests or Python tests may consolidate differently.
- **Contended timings.** The load average was 41 to 75 during the timings, with a spike above 130 just before the second session (S6 and our own mutation runs). The CPU saving is clear and repeats in both sessions. The parallel wall time was level in the first session (1,143 to 1,129 ms) and higher in the second (1,083 to 1,236 ms, with two slow after-repeats). An uncontended measurement was not possible.
- **Line coverage only.** Branch coverage was not compared.
- **Flaky coverage.** 8 lines before and 20 after are covered in only some repeats. The guardrail used the union over 3 repeats; 10 before lines are missed by at least one after repeat. More repeats might move a few lines either way.
- **Method B artifact.** A leaked async page load can count an uncalled inner function's lines as covered (the `detail.mjs:179–180` case). It was found and fixed here by adding a real test. Cupel's collector should not paint an omitted function with its parent's count in delta takes, or should confirm such lines with a per-file run.
- **Mutation scope.** The guardrail covers 3 modules (450 mutants); the extra 6 modules (665) were also checked. The other pipeline modules (editor internals, import, optimizer, shadow) were measured for coverage only. Equivalent mutants were not classified.
- **An S3 runner limit.** Runs started from the same out folder share the snapshot. One extra-module run overlapped our file changes. Its results from after the change (355) were discarded and re-run with the original files restored; a second run that saw the restored files was discarded and repeated (`mutx-after-suite-contaminated` in the raw outputs). Cupel's collector should stage the suite or lock it during a run.
- **Assay's test-count guard** (`node scripts/test-counts.mjs --check`) fails as designed: v2 (12) and volt (18) are "REMOVED", and `ui-pipelines.test.mjs` grew from 12 to 23. It counts `test(` declarations, and a table row counts once, so any consolidation looks like a loss. We did not run `--accept-loss` or change `tests/test-counts.json`. Cupel's `guard` evidence is exactly what a person needs before accepting that loss.
- **Whole-suite run** at the end (`node scripts/test-quiet.mjs`): 4,705 tests, 4,703 passed, 1 skipped and 1 failed, in 64.7 s wall (297 s user + 45 s sys). The failure is `merge-guards` › "test counts: the update script records additions, and refuses a loss unless told to".
