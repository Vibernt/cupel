# Test value system: market research

Research date: 2026-10-21. Web research only. Nobody was contacted, nothing was signed up for, no forms were submitted.

**Concept.** An independent "test value" system for agent-written code. It scores each test on unique coverage, unique mutation kills, real regressions caught, redundancy, cost and flakiness. It labels tests critical, standard or minor, and recommends keep, consolidate, rewrite or retire. Guardrails: a coverage ratchet, a mutation score floor, no removal of critical tests, and human approval. Agents get feedback while they write tests through MCP tools (`tests_check`, `tests_value`, `tests_plan`), and CI runs tests in priority order. It would ship as part of Vibernt Assay and also run standalone with GitHub Actions through JUnit and coverage upload.

**How reliable the sources are.** Many 2026 "tool roundup" pages are vendor blogs that copy each other. I used vendor pricing pages, docs, changelogs and arXiv papers wherever I could reach them. A fact marked *(secondary)* comes from an aggregator or a news write-up, not the primary source. A fact marked *(may be stale)* is older than 2025, or comes from a page that showed no date.

## 3. Production-ready methods (brief)

| Method | Status | Notes |
|---|---|---|
| **Minimization, selection, prioritization** (greedy set cover and HGS-style reduction, coverage-based selection, additional-coverage prioritization) | Textbook ([Yoo & Harman survey, STVR 2012](https://www.cse.chalmers.se/~feldt/advice/yoo_2010_regression_testing_survey.pdf)) *(old but standard)* | Public domain techniques. Minimizing on coverage alone is known to lose fault detection, so pair it with mutation and history. |
| **Predictive / ML test selection** | In production at Meta: about 2x lower test infra cost, >95% of test failures and >99.9% of faulty changes still caught ([arXiv 1810.05286](https://ar5iv.arxiv.org/html/1810.05286)). Also Launchable, Develocity, CircleCI and Datadog. | Commodity now, so it is not a differentiator. Assay already has selection. |
| **Transition-based prioritization** | Google TAP ([ICSE'19](https://research.google/pubs/assessing-transition-based-test-selection-algorithms-at-google/), [ICST'25 Transition Prediction](https://research.google/pubs/speculative-testing-at-google-with-transition-prediction/)) | Uses history of pass→fail transitions. | **Diff-based mutation testing** | Google: about 17M mutants over 760k changes, surfaced in code review, with "arid line" suppression ([TSE 2021](https://arxiv.org/pdf/2102.11378v1), [ICSE-SEIP 2018](https://web.eecs.umich.edu/~weimerw/2022-481W/readings/mutation-google.pdf)). | **Mutant subsumption / redundancy** | Arcmutate ships it ([docs](https://docs.arcmutate.com/docs/base-features.html)) | Tests that kill only subsumed mutants are candidates for retirement. |
| **Mutation-guided LLM tests** | Meta ACH in production ([arXiv 2501.12862](https://arxiv.org/abs/2501.12862)). MutGen-style feedback raises mutation score ([arXiv 2506.02954](https://arxiv.org/abs/2506.02954)). | Fits the `tests_plan` idea of telling the agent which surviving mutants to target. |
| **Flake detection by rerun / early flake detection** | Datadog, Mergify, Develocity | Commodity |

## 4. Gap analysis

### What nobody does well today

1. **One per-test worth score.** Vendors track flakiness (Datadog, Trunk, BuildPulse, Mergify, Codecov), duration (most of them), and selection relevance (Launchable, Datadog TIA, Develocity, CircleCI, Harness). No one combines *unique* coverage, *unique* mutant kills, **regressions confirmed by bisection**, cost and flakiness into one ranked score per test. Arcmutate test statistics (JVM only) and Tobari overlap (Go only, OSS) are the closest fragments.
2. **Removal advice with guardrails.** Selection tools *skip* tests per change but never recommend *deleting* them, so the suite and its maintenance cost keep growing. Nobody offers a reviewed "retire, consolidate or rewrite" workflow with a coverage ratchet, mutation floor and protected critical tests.
3. **Feedback at write time for agents.** The existing MCP tools are about flakiness (Trunk `fix-flaky-test`, Datadog flaky triage) or raw mutation runs (mutmut MCP, AdversaryGate for pytest). None answers "is the test you just wrote worth keeping, and which behaviours are still unprotected?" across languages.
4. **Telling real catches from noise.** "This test caught N real regressions" needs per-test history plus bisection to separate true catches from flakes. Assay already has both. Most flaky tools only label a test flaky or not.
5. **Agent-aware accounting.** Datadog excludes bots from committer counts ([Datadog](https://www.usagepricing.com/blueprint/datadog)), and Trunk counts non-bot committers ([Trunk](https://trunk.io/pricing)). Incumbent pricing and dashboards don't attribute test growth or CI cost to agent PRs, so the actual pain is invisible in their products.

### Strongest risks

| Risk | Severity | Why |
|---|---|---|
| **GitHub bundling** | High | Code Quality already does PR coverage and coverage rulesets at $10/committer, and Copilot generates the tests ([InfoQ](https://www.infoq.com/news/2026/08/github-code-quality/)). A "test value" tab would be a natural next step for them. |
| **Datadog / CircleCI / Codecov extension** | High | They already hold per-test history, coverage and an MCP surface. CircleCI shipped TIA GA eight days ago ([changelog](https://circleci.com/changelog/smarter-testing-is-now-generally-available/)). Adding a redundancy score is a small step for any of them. |
| **Mutation cost** | High | Full-suite mutation is expensive. Google made it work only with diff-based sampling and suppression ([TSE 2021](https://arxiv.org/pdf/2102.11378v1)). Per-PR runs must be limited to changed lines, with nightly full runs. LLM mutants (Mutahunter/ACH) add model cost and fall under AGENTS.md rule 6 (owner consent before expanding model use). |
| **Per-language integration** | High | Per-test coverage (which test covered which line) needs runner hooks for each language: Jest/Vitest, pytest, Go, JUnit/Gradle and so on. Standard JUnit plus lcov/Cobertura upload gives *aggregate* coverage only, so standalone mode can't compute unique coverage without a runner plugin or one coverage file per test. |
| **Trust in deletion** | Medium–high | One wrongly retired test that hides a production bug kills adoption. Retire must default to "quarantine as advisory, then human-approved removal", and the ratchets must be visible. |
| **Metric gaming / Goodhart** | Medium | Agents optimize whatever they are given (see the [tianpan.co](https://tianpan.co/blog/2026/05/17/test-agent-wrote-that-tests-nothing) "assertion laundering" pattern). The value score should not be fully exposed as a target, and mutation operators should rotate. |
| **Willingness to pay for "fewer tests"** | Medium | The ROI has to be stated as CI minutes, review time and escaped regressions, not as test count. |
| **Market fragmentation** | Medium | Buyers already pay for 2–3 adjacent tools (coverage, flaky, review bot). We must integrate with them, not ask buyers to replace them. |

## 6. Recommendation

**Build both, in sequence: first an Assay module, with a thin standalone ingest path from day one. Decide on a spin-out later, against hard criteria.**

Why a module first:
- The hard, defensible inputs already exist in Assay: per-test history, flakiness and quarantine, selection, **bisection** (needed for "real regressions caught"), and sharding (needed for cost per test). A standalone product would have to rebuild all of it.
- Assay's priority runs and selection get better with value labels. Value labels on their own are a feature that incumbents can copy.
- AGENTS.md scope fits. Mutation and coverage run in Cloudflare containers for Assay users. Standalone GHA users run them in their own runners, so Vibernt hosts no runners outside Cloudflare.

Why build the standalone path anyway (a GitHub Action that uploads JUnit, per-test coverage and mutation reports, plus the MCP server):
- It reaches the much larger GitHub Actions population without asking anyone to migrate CI.
- It tests the spin-out question cheaply.

**Go criteria for a spin-out** (review about 2 quarters after the module ships):
1. ≥10 standalone (non-Assay) design partners with ≥3 paying, and standalone accounting for ≥40% of active repos.
2. ≥30% of retire/consolidate recommendations accepted by humans, with **zero confirmed escaped regressions** from accepted retirements.
3. Measured CI test time reduction ≥20% on partner repos, with no drop in mutation score.
4. Per-PR changed-line mutation p50 ≤5 min and cost ≤$0.05 compute per PR in ≥2 languages (TS/JS + Python first, then Go or JVM).
5. Agents call the MCP tools on ≥50% of agent PRs in partner repos, with a measurable drop in redundant tests added per PR.
6. No incumbent (GitHub, Datadog, CircleCI, Codecov) has shipped per-test retire/consolidate advice by then.

**No-go / stay a module** if any of these hold: acceptance <15%, an escaped regression traced to a retirement, standalone users churn because the per-language setup is too heavy, or GitHub ships test-value scoring inside Code Quality.

**First proof point.** Run the analysis on the mastra and better-auth benchmark forks. Publish the agent-PR test redundancy, unique mutation kills and CI minutes recoverable. Section 2 found no public dataset that measures this directly.
